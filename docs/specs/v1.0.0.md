# v1.0.0 Product & Engineering Specification

## 1. User outcome

A user with a new project and no labeled dog examples can process a large archive and progressively reduce manual review. The system must make it obvious what to do next.

Primary workflow:

`New project -> Pipeline -> Review 50-100 -> Reclassify -> Review uncertain results -> Reclassify -> Repeat`

The user should never need to understand embeddings, nearest-neighbor internals, or model training to use this loop.

## 2. Functional requirements

### FR-1 Project bootstrap
- A new project starts with zero labeled examples.
- Existing project state must remain intact across restarts.
- Setup must document required dependencies and data locations.

### FR-2 Pipeline
- Existing scan/download/detection/embedding/classification stages remain usable.
- Jobs must expose progress and terminal status.
- A retry must not create duplicate logical records or corrupt existing state.
- A failed stage must provide enough information to diagnose the failure.

### FR-3 Review
- Review UI presents classification candidates and enough image context to make a decision.
- Accepting/correcting a result creates or updates a durable labeled example tied to the relevant embedding/crop.
- Re-reviewing an item must be idempotent and must not silently create duplicate training examples.
- The UI should prioritize uncertain/unreviewed items.

### FR-4 Reclassification
- Main page exposes an explicit `Reclassify` action.
- Reclassify reads the current labeled-example/embedding store.
- It recalculates nearest-neighbor predictions for eligible existing crops.
- It must not redownload or redetect images.
- It must not mutate the reviewed ground truth.
- It must be safe to rerun.
- A running reclassification job must not be started twice accidentally.
- Results should record the classification pass/job identifier and timestamp.

### FR-5 Classification semantics
- Use the existing nearest-neighbor embedding approach.
- Preserve a deterministic similarity/distance calculation.
- Define and document the confidence/decision policy currently implemented.
- Unknown/low-confidence outcomes must remain possible; do not force a dog label.
- Avoid data leakage: reviewed labels used as ground truth must not be counted as model successes merely because they supplied the label.

### FR-6 Metrics
At minimum expose:
- Total crops/images eligible for classification.
- Classified with a confident recommendation.
- Low-confidence/needs-review.
- Unknown/unclassified.
- Number of reviewed decisions.
- Number of labeled examples.
- Last classification/reclassification timestamp.
- Classification pass history.

Where defensible from stored data, calculate:
- Review coverage: reviewed eligible items / eligible items.
- Recommendation coverage: confident recommendations / eligible items.
- Review queue size.
- Per-pass change count: predictions changed after reclassification.

Do not claim precision/accuracy unless a held-out or otherwise valid ground-truth evaluation set exists.

### FR-7 Dashboard
The main page should communicate:
- Current project state.
- Pipeline/reclassification job status.
- Review queue size.
- Labeled-example count.
- Recommendation coverage.
- Last reclassification.
- A compact trend view over classification passes or review batches.

Metrics must be based on persisted data, not browser-only counters.

### FR-8 Observability
- Log job start/end, counts, durations, failures, and major stage transitions.
- User-facing errors should be actionable without exposing secrets or sensitive paths unnecessarily.
- Long-running jobs should be distinguishable from stale/failed jobs.

### FR-9 Performance
- Reclassification must process only eligible existing crops.
- Avoid recomputing embeddings when the source embedding is already valid.
- Use batching where supported by the current architecture.
- Do not load an entire 30,000-image archive into browser memory.
- Database queries must avoid obvious N+1 patterns.

### FR-10 Documentation
Document:
- New-project workflow.
- Recommended initial review batch.
- When to run Reclassify.
- Meaning of confidence/unknown/review states.
- How to recover from failed jobs.
- Backup/state expectations.
- Known limitations.

## 3. Responsible architectural guidelines

1. **Preserve the existing architecture unless a change is necessary.** Prefer small, composable additions over rewrites.
2. **Separate ground truth from predictions.** A user review is authoritative input. A classifier recommendation is derived state.
3. **Make derived state reproducible.** Classification results should be recomputable from embeddings, labels, and the classifier configuration.
4. **Use explicit job boundaries.** Pipeline and reclassification should have durable job records/status where the current system supports jobs.
5. **Design for idempotency.** Retrying any operation must be safe.
6. **Avoid hidden side effects.** Reclassify must not alter reviewed labels.
7. **Keep ML policy centralized.** Thresholds, distance metrics, and candidate-selection logic should live in one service/module rather than being duplicated in UI code.
8. **Prefer migrations over destructive schema edits.** Existing user state must survive upgrades.
9. **Validate at boundaries.** Do not trust IDs, file paths, uploaded metadata, or client-supplied classification values.
10. **Do not manufacture confidence.** If the current nearest-neighbor score does not support a reliable probability, call it a score/similarity or confidence proxy, not calibrated probability.
11. **Protect privacy.** Avoid logging image contents, credentials, tokens, or unnecessary personal metadata.
12. **Bound resources.** Batch large operations and provide cancellation/recovery semantics if practical.
13. **Keep browser responsibilities thin.** The server/backend owns long-running work and persistence.
14. **Maintain backward compatibility.** Existing projects and previously reviewed images should continue to work after upgrade.

## 4. Suggested data model concepts

Adapt these to the current schema rather than creating duplicates:

- `Project`
- `Crop/Image`
- `Embedding`
- `Dog/Label`
- `Review` or authoritative label assignment
- `ClassificationResult`
- `ClassificationPass` / `Job`
- Optional metric snapshot/pass summary

A classification result should distinguish at least:
- subject/crop identifier
- predicted label (nullable)
- similarity/distance score
- decision state: confident / review / unknown
- classifier configuration/version
- pass/job identifier
- created/updated timestamps

A review/ground-truth record should distinguish:
- subject/crop identifier
- accepted label
- reviewer action
- timestamp
- source of truth

## 5. Reclassification behavior

Recommended sequence:

1. Acquire a project-scoped job lock.
2. Create a classification-pass record.
3. Load current valid labeled examples.
4. Select eligible existing crops with valid embeddings.
5. Compute nearest-neighbor candidates in batches.
6. Apply centralized decision thresholds.
7. Write predictions transactionally or in safe batches.
8. Preserve all reviewed/ground-truth assignments.
9. Record counts and duration.
10. Mark pass complete or failed.
11. Release lock.

If no labeled examples exist, the operation should terminate cleanly with an explanatory status rather than failing.

## 6. Metrics semantics

Use explicit denominators and scopes. Every metric should state what population it measures.

Recommended:
- `eligible_count`
- `reviewed_count`
- `labeled_example_count`
- `confident_count`
- `needs_review_count`
- `unknown_count`
- `coverage = confident_count / eligible_count`
- `review_rate = reviewed_count / eligible_count`
- `prediction_change_count` between consecutive passes

For evaluation metrics such as precision/recall, create a separate held-out evaluation set. Do not calculate them from the same reviews used to populate the nearest-neighbor store.

## 7. Acceptance criteria

A release candidate is acceptable when:

- A fresh project can be created successfully.
- A representative image set can run through the full pipeline.
- A user can review 50-100 items and see the labeled-example count increase appropriately.
- Reclassify can be launched from the main page.
- Reclassify updates predictions without altering reviewed labels.
- Re-running Reclassify produces stable results when inputs/configuration have not changed.
- A second review/reclassify cycle works.
- Failed/restarted jobs do not duplicate or corrupt state.
- Dashboard metrics agree with persisted database counts.
- A 30,000-image-scale dry run or representative load test demonstrates bounded memory use and acceptable batching.
- Documentation describes the workflow and recovery path.
- Existing projects pass regression tests.

## 8. Explicit non-goals for v1.0.0

- Temporal weighting by image date.
- Automatic learned-model training.
- Personalized per-dog neural classifiers.
- Calibrated probability scores unless separately implemented and validated.
- Fully autonomous labeling with no review path.
- Distributed/cloud-scale orchestration.
