# v1.6.0 — Pet Insights

## Purpose

Dog Tagger's core job is accurate individual pet identification. Once an identification is
confirmed, it sits next to metadata Immich already computed for free — capture time, GPS/location,
and Immich's own recognized people. This spec adds a small, deliberately-scoped "fun layer" that
combines confirmed identifications with that existing metadata to answer simple, factual questions
("how many photos of this pet do we have," "where has it been," "who does it usually appear
with") — without turning the project into a general-purpose photo analytics tool.

Tracking issue: [#94](https://github.com/bradreimer/immich-dog-tagger/issues/94).

## User story

As an owner reviewing my library, once a pet has enough confirmed photos, I want to see simple
derived facts about that pet — photo count, date range, most-common places, and who they're most
often photographed with — without leaving the app, and without the app inventing conclusions it
can't back up with the underlying data.

## Goals

- Persist a settled, per-(photo, pet) fact table (`PetOccurrence`) built from existing
  classification/review state, not a new source of truth for identity.
- Cache the Immich-provided per-photo facts needed for insights (GPS/location, recognized people,
  favorite flag) directly on `Asset`, refreshed on scan.
- Compute insights (summary counts, timeline, places, people) at read time from those facts —
  never store a conclusion like "favorite human" as a column.
- Expose insights as read-only API endpoints, and a read-only per-dog UI page.
- Keep this additive: no change to the review workflow, no writes back to Immich.

## Non-goals (this iteration)

- Best Friends (pet-to-pet co-occurrence), On This Day, Pet World Tour map, and Milestones —
  explicitly deferred to a follow-up once the base fact table and Phase 1-6 experiences (per issue
  #94) are in use. Not implemented in this iteration.
- Any personality inference or narrative text presented as fact.
- AI-generated slideshows/stories.
- Writing conclusions or metadata back to Immich.
- A precomputed/materialized insights cache — plain aggregation over one pet's occurrences is
  cheap enough at the scale a single-household library reaches; revisit only if that stops being
  true.
- Endpoint-level API auth — tracked separately as an existing known gap
  (`docs/status.md`); insights endpoints follow the same (current lack of) auth as every other
  route in this API.

## Requirements

### Data

- `Asset` gains cached, nullable Immich-derived fields: `latitude`, `longitude`, `country`,
  `state`, `city`, `is_favorite`, `people` (JSON list of `{"id": str, "name": str | None}`), and
  `metadata_synced_at`. Populated from the same `/api/search/metadata` response the scanner
  already fetches (`exifInfo`, `people`, `isFavorite`) — no additional Immich API call.
- New `PetOccurrence` table: one row per settled `(asset, identity)` pairing, built from the
  current `CropClassification` state (`identity`, `confidence`, `source`), with a foreign key back
  to the classification for provenance. Not written to directly by any UI/API — only materialized
  by `PetOccurrenceService` as a side effect of classification/correction/reclassification.
- A classification with no identity (`None`/`"Unknown"`) has no `PetOccurrence` row. A row is
  deleted if its classification's identity is cleared or changed away.

### Behavior

- `PetOccurrenceService.sync_classification(classification)` keeps one `PetOccurrence` in sync
  with one `CropClassification`'s current state. Called after auto-classification
  (`ClassificationService`), review correction (`ClassificationCorrectionService`), and
  reclassification (`ReclassifyService`) — so `PetOccurrence` never drifts from the classification
  state it's derived from.
- `PetOccurrenceService.sync_all()` rebuilds every occurrence from current classification state,
  for backfilling a library that already has classification history predating this feature.
  Exposed as `immich-dog-tagger backfill-occurrences`.
- `InsightsService` computes, per identity, from that identity's `PetOccurrence` rows joined to
  `Asset`:
  - `summary`: total distinct photos, first/last seen dates, per-year counts, top place, top
    person (when data exists — no fabricated placeholders when it doesn't).
  - `timeline`: chronological occurrences, paginated.
  - `places`: photo counts grouped by (city, state, country).
  - `people`: photo counts grouped by Immich-recognized person.
  All computed in Python over one identity's occurrences (bounded, single-household scale) —
  deterministic, explainable, no hidden ranking model.

### API

Read-only, under `/api/dogs/{identity_id}/insights/`: `summary`, `timeline`, `places`, `people`.
404 if the identity doesn't exist. No endpoint writes to `PetOccurrence`, `Asset`, or Immich.

### UI

A new "Insights" view reachable per-dog from the existing Dogs & Cats page, showing the same data
the API exposes: summary stat cards, a places list, a people list, and a timeline. Any inference
beyond a plain count (there is none in this iteration — no "favorite" label is applied without a
human-readable count backing it, e.g. "Most often with Brad (112 photos)" rather than an
unqualified "Favorite Human: Brad") is visually distinguished as derived, not stated as fact.

## Acceptance criteria

- Given a pet with confirmed identifications across several photos with GPS/location and
  recognized-people data, `GET /api/dogs/{id}/insights/summary` returns accurate total-photo,
  date-range, and top-place/top-person counts computed from `PetOccurrence`+`Asset` data.
- Given a photo whose classification is corrected from one identity to another via review, the
  old identity's `PetOccurrence` for that photo is removed and the new identity's is created,
  without a manual sync step.
- Given a classification cleared to `Unknown`, its `PetOccurrence` row is removed.
- Given an existing library with classification history predating this feature,
  `immich-dog-tagger backfill-occurrences` populates `PetOccurrence` for every currently-settled
  classification.
- Insights endpoints and the UI page never display a location or person value more precise than
  what Immich itself already exposed to the local cache — no data is invented, and none is sent
  to any external service.
- `docs/status.md`'s existing "endpoint-level API auth not implemented" gap is referenced, not
  silently expanded without note, in the privacy section of issue #94 and this spec.

## Open questions

- Should `Asset.people`/location be refreshed only on new-asset scan, or on every scan cycle
  (covers a photo whose Immich favorite/people tags changed after initial scan)? This iteration
  refreshes on every scan cycle, since the data is already in the response the scanner fetches —
  revisit if that turns out to be measurably slower for very large libraries.
- Exact display precision for GPS coordinates (exact lat/long vs. city/country-only by default) is
  a UI polish question deferred to implementation; this iteration surfaces city/state/country
  text, not a coordinate map (the map view is explicitly deferred, see Non-goals).
