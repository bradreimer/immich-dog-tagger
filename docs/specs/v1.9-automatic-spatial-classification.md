# v1.9 Automatic Spatial Classification

## Purpose

v1.5.0 (#91, [ADR-003](adr/ADR-003-automatic-temporal-recency-classification.md)) taught
`IdentityClassifier` to weigh how closely a candidate reference example's `captured_at` aligns
with the photo being classified, so that when two identities look visually very similar, the one
whose reference photos are closer in time to the query photo wins. The owner has observed the same
disambiguation applies to *where* a photo was taken: two visually similar dogs are often
photographed in different, characteristic places (different owners' homes, different regular walk
routes, different yards), so location is frequently exactly the signal a human reviewer reaches
for when two dogs "look very similar."

`Asset.latitude`/`longitude` already exist and are already populated from Immich's EXIF GPS data
(issue #94, added for the read-only Pet Insights "Places" view), but nothing in the classification
path uses it. This spec extends the same continuous, fail-open weighting approach v1.5 established
for time to geographic distance, reusing its exact shape rather than inventing a new mechanism.

## User story

As the owner, when two dogs or cats look visually very similar, I want the classifier to also
weigh where a photo was taken, so that a photo taken in one identity's usual places is favored over
a visually-tied identity whose reference photos were all taken somewhere else -- without me
configuring anything.

## Goals

- Score each candidate example using visual similarity, capture-date proximity (already shipped),
  and now also how close the example's own location is to the photo being classified.
- Weight examples taken within a couple of kilometers fairly strongly, decaying gradually beyond
  that, with a floor that never reaches zero -- a lone identity with only far-away examples and no
  closer competing identity must still classify correctly.
- Fail open exactly as `captured_at` does: a photo or an example with no GPS data participates at
  full weight. Absence of location evidence is never a penalty.
- Never let the spatial signal manufacture, inflate, or deflate the reported confidence number for
  the winning match -- it only influences *which* example/identity wins the comparison, preserving
  the existing rule that `similarity` stays a raw, uncalibrated embedding score (v1.0.0.md section
  8; the same constraint v1.5's `temporal_weight` already respects).
- Surface a `location-mismatch` review reason, alongside the existing `temporal-mismatch`, so the
  owner still sees why a match is uncertain.

## Non-goals

- No owner-facing setting to tune the decay curve (its characteristic distance scale, or its
  floor) in this pass -- same stance v1.5 took for its own temporal scale. Ship one sane default
  as a code constant; revisit if usage shows it's wrong for a real library.
- No reverse geocoding or place-name-based comparison (e.g. matching on the cached
  `country`/`state`/`city` fields). This uses raw latitude/longitude distance only; the
  geocoded fields stay Insights-only for now.
- No change to the underlying nearest-neighbor approach beyond this scoring adjustment: still
  per-example cosine similarity, still one winning example per identity, still governed by
  `ClassifierPolicy`'s threshold and candidate limit.
- Does not retroactively recompute existing `CropClassification` rows. The next Reclassify pass
  (the existing mechanism for any classifier-version change) picks up the new scoring.
- Does not touch bulk bootstrap import (`Learner.learn()`/`ReviewImporter`): those already classify
  with no `captured_at` either, since a whole directory of images has no single capture date or
  location to attribute. Location is only sourced per-photo, the same population `captured_at`
  is sourced for today (crop -> detection -> asset, at classify/correct/reclassify time).

## Requirements

### FR-1: `EmbeddingExample` gains a location snapshot

`EmbeddingExample` gains nullable `latitude`/`longitude` columns, denormalized from the source
`Asset` at the moment an example is learned -- the same treatment `captured_at` already gets.
Additive migration; existing rows get `NULL` (unknown location, not "at 0,0").

### FR-2: Spatial weight as a function of distance

`SimilarityScorer` computes a `spatial_weight` in `[SPATIAL_FLOOR, 1.0]` from the great-circle
(haversine) distance between the crop's own location and a candidate example's own location:
`1.0` when the coordinates coincide, decaying toward a floor (never reaching it) as the distance
grows, with a characteristic scale of a few kilometers. `spatial_weight` is `1.0` whenever either
side is missing a coordinate -- the same fail-open guarantee `temporal_weight` makes for dates.

### FR-3: Weighted ranking, unweighted reported confidence

For each identity, `IdentityClassifier` selects the example that maximizes
`similarity * temporal_weight * spatial_weight` (not similarity or temporal weight alone) as that
identity's best match, and ranks candidates by the same combined score. The `similarity`/
confidence reported for the winning candidate remains that example's raw cosine similarity --
neither `temporal_weight` nor `spatial_weight` ever changes what confidence number is shown or
compared against `ClassifierPolicy.confident_threshold`.

### FR-4: Candidate transparency

`ClassificationCandidate` exposes `spatial_weight` alongside the existing `temporal_weight`,
persisted in `CropClassification.candidates` the same way.

### FR-5: Review reason

`ReviewQueryService._review_reason()` surfaces `location-mismatch` when the accepted/top
candidate's `spatial_weight` falls below a fixed low-alignment threshold, checked alongside the
existing `temporal-mismatch` check (temporal is checked first; either firing is enough to flag the
item -- this pass does not attempt to represent "both misaligned" as a distinct reason). A
candidate whose weight is `1.0` -- whether because the locations aligned or because a coordinate
was missing -- is never flagged, preserving fail-open behavior.

### FR-6: Schema

Add `latitude`/`longitude` to `EmbeddingExample` via an additive migration, following
`_ensure_asset_metadata_columns`'s pattern. No data loss for existing installs: existing examples
simply have no location on this signal, same fail-open outcome as a missing `captured_at`.

## Acceptance criteria

- Classifying a photo whose location sits close to one identity's own example locations, and far
  from a visually similar competing identity's example locations, selects the geographically
  closer identity even when raw cosine similarity between the two candidates is nearly equal.
- Classifying a photo with no location data, or against an identity whose examples all lack
  location data, behaves exactly as it would with spatial weighting disabled (uniform weight of
  `1.0`).
- A single-identity candidate with no competing identity still reports its true raw similarity as
  confidence regardless of how far away its examples were taken -- distant examples alone, with
  nothing to disambiguate against, must not demote an otherwise-confident match to needs-review.
- Temporal and spatial weighting combine correctly: a candidate example close in time but far in
  distance, and one far in time but close in distance, are both partially discounted rather than
  either signal alone deciding the outcome.
- Tests cover: distance breaks a near-tie in the geographically closer identity's favor, the floor
  prevents a distant example from being fully excluded, missing coordinates on either side fail
  open, and the combined temporal x spatial weighting.

## Open questions

- Should the decay curve's scale/floor become an owner-tunable setting, and should it differ by
  identity (e.g. a dog that travels frequently vs. one that never leaves home)? Starting fixed;
  revisit if real usage shows the default doesn't fit a particular library, same as v1.5's own
  open question about its temporal scale.
- Should `location-mismatch` and `temporal-mismatch` be reported together when both fire, instead
  of temporal taking precedence? Not scoped here -- revisit if owners report the single-reason
  badge is misleading when both signals disagree.
