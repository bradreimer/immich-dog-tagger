# v1.11.0 — Library as a Browse-and-Correct Catalogue

Tracking issue: [#196](https://github.com/bradreimer/immich-dog-tagger/issues/196).

## Purpose

v1.8.0 turned the Library into an identity-first *approval workspace*: pick a species, pick a pet,
approve clusters of that pet's pending recommendations. That solved a real problem -- labeling
cost scaling with pets instead of photos -- but it also removed the thing the Library used to be
good at: opening the whole catalogue, narrowing it with a few independent filters, and looking at
one photo at a time to check or fix its classification. An owner who wants "show me every
unreviewed dog photo from last August" or "find this one specific photo of Fibs and fix it" has to
first commit to a pet, which the cluster workspace assumes is already known.

This spec puts that flat, filterable, sortable, paginated catalogue back as the Library's primary
(and now only) view, with a details panel that surfaces everything about a selected photo and a
direct path to fix it. It supersedes the FR-1 species/pet selector and FR-2/3/4 cluster-approval
panels as the Library's UI (see "Relationship to v1.8.0" below) -- the underlying correction
service, provenance, and the cluster/approval *backend* are untouched and keep working exactly as
they do today; they are simply no longer the Library page's entry point.

## User story

As the owner reviewing a large, already-classified library,
I want to filter, sort, and page through every classified photo, click one to see its full detail,
and jump straight to fixing it,
so that I can audit and correct the catalogue by whatever axis matters right now -- date, pet,
species, or review status -- not only by picking a pet first.

## Goals

- Independent filters: species, pet (identity), reviewed status, and a captured-date range, each
  usable alone or combined, all as `<select>`/date-input controls -- no selection step gates the
  others.
- Two sort orders: by capture date and by confidence, each with a sensible default direction
  (newest first; most confident first).
- A thumbnail grid, paginated 50 at a time.
- Clicking a thumbnail opens a details panel for that photo: name (predicted/confirmed identity),
  species, confidence, capture date, location, review status, a link to the photo in Immich, a
  link to Photo Lookup, and an "Edit" link into the Review page for that exact photo.
- The Review page accepts any classification by id via a URL parameter and lets the owner set its
  identity, correct its species, or mark it as not a dog or cat at all -- not only step through the
  active review queue.

## Non-goals

- Deleting the cluster-based bulk approval/rejection/reassignment backend
  (`RecommendationClusterService`, `ConfirmedClusterService`, `ClusterApprovalService`, the
  `/library/clusters*` routes) or its tests. Nothing in this spec removes that capability from the
  app; it stops being reachable from the Library page's primary view. See "Open questions" for
  what happens to it next.
- Changing `POST /classifications/{id}/correct`, `.../species`, or the not-animal endpoints'
  semantics. This spec adds one new read endpoint and extends `GET /api/library`; it changes no
  existing write path.
- Multi-select or bulk actions in the flat grid. One photo, one details panel, one Edit link --
  consistent with the catalogue being a browse-and-correct surface, not an approval workspace.
- An inline correction control on the details panel itself. Corrections happen on the Review page,
  reached via the Edit link -- one editing surface for a classification, not two.
- Creating a new pet identity from the Library or Review page. Identity management stays on the
  Dogs & Cats page, unchanged.
- FR-11's "rescue a missed detection" (`UndetectedPanel`) was unrelated to this change and
  untouched by it. (It was later removed entirely, unrelated to this spec, by
  [#200](https://github.com/bradreimer/immich-dog-tagger/issues/200).)

## Relationship to v1.8.0

v1.8.0 ([docs/specs/v1.8-library-approval-workspace.md](v1.8-library-approval-workspace.md)) is not
retracted: FR-6 (rejection), FR-8 (coverage, now on Metrics), FR-9 (sensitivity/auto-reclassify),
and FR-10 (merge, now on Dogs & Cats) all shipped independently of the Library page's layout and
are unaffected. What changes here is narrower than it looks: FR-1's species/pet selector and
FR-2/3/4's cluster panels stop being *the Library page*. See [ADR-008](../adr/ADR-008-library-flat-browse-workspace.md)
for the fuller reasoning and what stays.

## Requirements

### FR-1 — Independent filters

1. Species: `All species` / `Dog` / `Cat`, a `<select>`.
2. Pet: a `<select>` listing active identities (`GET /dogs?include_inactive=false`), each labeled
   with its species so "All species" doesn't produce ambiguous duplicate names; scoped to the
   selected species when one is chosen, and reset to "All pets" if the current selection no longer
   matches a species change (mirrors FR-1's existing invalidation rule from v1.8.0).
3. Reviewed status: `All` / `Reviewed` / `Unreviewed`, a `<select>`.
4. Captured-date range: two date inputs, "Captured between _ and _", inclusive, either end
   optional. Reuses `GET /api/library`'s existing `captured_after`/`captured_before` semantics
   unchanged.
5. All four filters combine with AND semantics via the existing query parameters
   (`identity`, `species`, `reviewed`, `captured_after`, `captured_before`); none of them requires
   another to be set first.
6. Any filter change resets pagination to the first page.

### FR-2 — Sort

1. A sort `<select>` with two entries: "Newest first" (capture date, descending) and "Most
   confident first" (confidence, descending) -- the two axes the owner asked for, each defaulting
   to the direction that matches how the rest of the app already ranks these values (Library's
   previous implicit order was newest-first; clusters already default to confidence-descending).
2. `GET /api/library` gains a `sort` query parameter reusing the existing `ClusterSort` enum
   (`captured_desc` default, `captured_asc`, `confidence_desc`, `confidence_asc`) -- no new enum,
   since the four orderings are identical in meaning to what clustering already sorts by.
3. Sorting happens at the SQL level (`ORDER BY`), not by sorting an already-paginated page in
   memory -- unlike cluster sorting, which sorts a single bounded in-memory pool, the library
   paginates over a potentially large filtered set, so the order must be established before
   `LIMIT`/`OFFSET` is applied.
4. Photos with no capture date sort last under both date directions, matching the null-handling
   convention `RecommendationClusterService` already established; ties are broken by
   `classification_id` ascending so identical confidences or dates don't reorder between requests.

### FR-3 — Thumbnail grid and pagination

1. Every matching classification renders as a thumbnail card (crop image, predicted/confirmed
   identity, reviewed/unreviewed indicator).
2. 50 results per page (`limit=50`), with Previous/Next controls and an "X-Y of N" range label,
   reusing the existing pagination pattern.
3. Clicking a card selects it; the selected card is visually distinguished and opens the details
   panel.

### FR-4 — Details panel

1. Opens when a thumbnail is selected; shows: name (`prediction.identity`, or "Unknown"), species,
   confidence (`prediction.similarity`), capture date, location, review status
   (reviewed/unreviewed, and the reviewed timestamp when known), a "View in Immich" link
   (`ImmichPhotoLink`, reused as-is), a "View in Photo Lookup" link (`PhotoLookupLink`, reused as
   -is), and an "Edit" link to `/review?classification_id={id}`.
2. Location is derived from the same cached `Asset.city`/`state`/`country` fields Insights already
   reads (issue #94/#129) -- `"city, state, country"`, joined on whichever parts are present, or
   absent entirely when none are. No new data source, no Immich call from the browser.
3. Selecting a different photo replaces the panel's contents; changing a filter, sort, or page
   clears the selection (a stale panel for a photo no longer in view is worse than no panel).

### FR-5 — Edit any classification from Review

1. `GET /api/classifications/{id}` returns the same `ReviewItemResponse` shape `/review` already
   uses, for exactly one classification -- the read side of "any image via URL params".
2. The Review page reads an optional `classification_id` query parameter on load. When present, it
   loads that one classification via the new endpoint instead of the active review queue, and
   renders the same correction surface (`ReviewCard`: identity chooser, species chooser, and the
   not-animal toggle added by this spec) with no queue chrome (no Previous/Next-through-queue, no
   Skip, no filter buttons, no progress bar) -- there is no queue in this mode, only this one photo.
   A "Back to Library" link returns to `/library`.
3. Without the parameter, the Review page behaves exactly as it does today: the active queue, in
   its existing order, with Skip/Previous/Next and the existing filter buttons.
4. `ReviewCard` gains a "Not a dog or cat" toggle (mirroring Photo Lookup's `DetectionList` row),
   reusing the existing `POST`/`DELETE /crops/{crop_id}/not-animal` endpoints -- available in both
   the queue and the single-item mode, since it is the same correction surface either way.
   `ReviewItem`/`ReviewItemResponse` gain a `not_animal` field (read from `Crop.not_animal`) so the
   toggle can render its current state.

## Acceptance criteria

- Species, pet, reviewed-status, and date-range filters each work alone and in combination; a pet
  no longer matching a changed species is cleared; changing any filter or the sort resets
  pagination to page 1.
- Sorting by date and by confidence both order the full filtered set (verified across a page
  boundary, not just within one page); a photo with no capture date sorts last under both date
  directions; ties break by classification id.
- The grid pages 50 at a time with working Previous/Next and an accurate range label.
- Selecting a thumbnail shows a details panel with all nine listed fields/links, matching the
  selected photo; changing filters/sort/page clears the selection.
- The Edit link opens `/review?classification_id={id}` showing that exact photo, correctable by
  identity, species, or not-animal, with no dependency on where it sits in the active queue (it may
  not be in the active queue at all -- e.g. an already-reviewed or confidently-classified photo).
- `/review` with no query parameter is behaviorally unchanged: same queue, same filters, same
  Skip/Previous/Next/progress bar.
- `GET /api/classifications/{id}` returns 404 for an id that doesn't exist and the same
  `ReviewItemResponse` shape as a queue item otherwise.
- Vitest covers: each filter's query params, the species-change pet-reset, sort selection, page
  reset on filter/sort change, selection-clears-on-filter-change, and the Review page's
  single-item mode (rendering from `classification_id`, hiding queue chrome, the not-animal
  toggle). Pytest covers: `library()`'s `sort` parameter (both axes, both directions, the
  null-last rule, the id tiebreak) across a paginated boundary; `location`/`not_animal` on
  `ReviewItem`; and the new `GET /classifications/{id}` endpoint (200 and 404).

## Open questions

- **What becomes of the cluster-approval workspace UI removed from the Library page?** The backend
  stays; nothing currently links to it from the app. Candidates: a separate `/approve` page, a
  second Library tab, or leaving it unreachable from the UI until there's a concrete need. Deferred
  -- not blocking this spec, and reversible either way since no code is deleted.
