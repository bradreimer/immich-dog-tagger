# v1.1 Automation Coverage Dashboard

## Purpose

DT-1006 (v1.0.0) shipped a `GET /metrics` endpoint answering "is manual review
becoming less necessary?" with point-in-time counts and a basic pass-history
trend. This spec covers the gap between that and the fuller dashboard an
operator actually wants: a queue that shrinks visibly pass over pass, a
labeled-example count that grows visibly, and one prominent number that says
how much manual work the system is currently saving.

## User story

As the operator of a project, after each Reclassify pass I want to see the
review queue shrinking, the labeled-example count growing, and one clear
"N% of images require no manual review" number -- so I can tell whether the
review -> reclassify loop is actually working, without misreading a bare
nearest-neighbor similarity score as validated accuracy.

## Goals

- Make the full trend story -- review queue size, confident rate, unknown
  rate, labeled-example count, and predictions-changed -- queryable across
  classification passes, not just confident/needs-review/unknown/changed.
- Make "review queue" mean the same thing everywhere it's used: the set of
  items a human would actually need to look at (unknown + low-confidence +
  candidate-conflict, excluding anything already reviewed) -- matching what
  `/review` actually returns, not the narrower definition `/metrics`
  currently derives.
- Surface one prominent, explicitly-named "automation" metric via the API:
  how many/what percentage of eligible images currently need no manual
  review at all.

## Non-goals

- Calibrated probability, precision, recall, or any "accuracy" framing for
  the nearest-neighbor similarity score. No held-out evaluation set exists;
  this remains out of scope until one does (see `docs/specs/v1.0.0.md`
  section 8 for the same constraint carried forward).
- Per-dog confusion analysis / model-quality section. Explicitly deferred to
  a future "model quality" milestone, as called out in the v1.0.0 spec.
- New UI chart types beyond what's needed to plot the additional trend
  fields this spec adds to the API (chart work belongs to whichever ticket
  consumes the new fields, informed by the `dataviz` design guidance already
  used for the existing coverage sparkline).

## Requirements

### FR-1: Per-pass trend completeness

Every `ClassificationPass` must record, at the time it completes:

- `labeled_example_count`: the labeled-example count at that point in time
  (today this is only queryable as a live, present-tense count -- not
  historically, so a trend line can't be drawn).
- `review_queue_size`: the actual review-queue size at that point in time
  (see FR-2 for the definition), not just the narrower `needs_review_count`.

### FR-2: Consistent review-queue definition

`review_queue_size` (both the live `/metrics` value and the per-pass
snapshot from FR-1) must count the same population `GET /review` surfaces:
items with no review action yet, where either identity is unknown, or
confidence is below the confident threshold, or there's a candidate
conflict. Today's `needs_review_count` in `/metrics` (identity set but below
threshold) undercounts this in practice, since the classifier currently
never sets an identity below its own threshold -- it is effectively always
0 outside contrived cases.

### FR-3: Rate fields for every count that has one

`unknown_rate` (unknown_count / eligible_count) must be exposed alongside
the existing `coverage` (confident) and `review_rate` (reviewed), so every
top-level count with a natural denominator has its ratio computed
server-side rather than left to the client -- consistent with the existing
"denominators must be explicit" principle from DT-1006.

### FR-4: Prominent automation metric

`/metrics` must expose an explicitly-named, headline automation metric --
e.g. `automation_rate` and `no_review_needed_count` -- representing
"eligible images that currently need no manual review." Whether this is a
straight alias of `coverage`/`confident_count` or a distinct population
that also folds in already-reviewed/confirmed items is an open question
(see below) to resolve during implementation, not before.

### FR-5: Dedicated Metrics tab

Metrics get their own top-level navigation tab, separate from both Mission
Control (operational actions: jobs, diagnostics, manual operations,
schedules) and Review (the correction workflow). The Learning Progress card
DT-1006 placed on Mission Control moves there -- it does not stay on
Mission Control and it is never duplicated onto Review.

## Acceptance criteria

- `GET /metrics` returns `unknown_rate` and a prominent automation metric.
- `GET /metrics`'s `pass_history` entries include `labeled_example_count`
  and `review_queue_size` for every pass going forward.
- `review_queue_size` (live and per-pass) matches what `GET /review` would
  return as pending work, verified with a shared test fixture/scenario.
- No new field implies or states a calibrated accuracy/probability.
- Existing DT-1006 fields and behavior are unchanged (additive only).
- Metrics are visible on their own tab and are not present on Mission Control or Review.

## Open questions (resolved)

- **Does `automation_rate` include already-reviewed items, or only
  currently-confident AUTO predictions?** Resolved: it includes both --
  `no_review_needed_count = eligible_count - review_queue_size`, i.e. the
  complement of the review queue. Rationale: the metric answers "how many
  images can I ignore right now," not "how many did the classifier get
  right without help." An already-reviewed item needs no *further* review
  regardless of its confidence, so excluding it would undercount and
  misrepresent how much manual work is actually left.
- **Should `review_queue_size` per-pass be backfillable?** Resolved: no.
  `ClassificationPass.labeled_example_count`/`review_queue_size` are
  nullable and only populated going forward (DT-1101); existing passes
  keep `null` for both rather than a fabricated/reconstructed value.
