# v1.10.0 — Pet Album Browsing

Tracking issue: [#183](https://github.com/bradreimer/immich-dog-tagger/issues/183).

## Purpose

v1.8's [Library approval workspace](v1.8-library-approval-workspace.md) turned the Library into
a pet-first surface for *pending* recommendations: pick a pet, see its unreviewed candidates
grouped into similarity clusters with a confidence range, approve or reassign a whole cluster at
once. That work deliberately scoped clustering to the unreviewed pool
(`RecommendationClusterService._candidate_ids()` excludes any classification with a
`ReviewAction`); once a photo is confirmed for a pet, it drops out of the cluster panel and back
into the flat, ungrouped, one-photo-at-a-time grid `LibraryPage.tsx` has shown since DT-1112.

That flat grid is the gap this spec closes. Browsing a pet's *confirmed* photos today means paging
through a plain grid with no grouping and no confidence signal, and fixing a bad one means
one photo at a time through `LibraryEntryCard`'s per-card dropdown. Every comparable "album" view
(Lightroom Classic, Apple Photos, Immich's own People) lets the owner look at a subject's whole
confirmed set clustered by similarity and move a mis-grouped photo or a whole visually-similar
group to a different subject in one action. This spec brings that same treatment — already built
for the pending queue in v1.8 — to a pet's confirmed photos, so the album view and the correction
workflow it enables cover everything the owner sees for that pet, not only what is still waiting
on a decision.

No new model, no new pipeline stage, no change to classification policy. This reuses
`clustering.py`'s existing agglomerative-over-cosine-distance clustering and the `useSelection`
hook `#142` built and explicitly left for this caller (see `docs/status.md` "Next Work": *"#142's
`useSelection` hook is the reusable primitive for the multi-select the flat library grid still
lacks"*).

## User story

As the owner of a library with dogs or cats already confirmed,
I want to see a pet's confirmed photos clustered by similarity with their confidence, and move a
photo or a whole cluster to a different pet in one action,
so that fixing a mistake in what I've already confirmed costs one decision instead of one photo,
the same way approving a new recommendation already does.

## Goals

- Extend the pet-scoped Library view so a pet's **confirmed** photos are also grouped into
  visual-similarity clusters, each showing a confidence value (or range, for a multi-photo
  cluster) and a capture-date range — the same presentation `ClusterPanel`/`ClusterCard` already
  give the pending queue.
- Let the owner select a photo, several photos, or a whole cluster within that confirmed view and
  move the selection to a different pet in one action, using the multi-select and reassignment
  patterns v1.8 already shipped (`useSelection`, the `reassignCluster` write path).
- Keep every move an ordinary correction: same `ClassificationCorrectionService`, same
  `ReviewAction` provenance, same next-sync album reconciliation. Nothing here is a new kind of
  state or a second write path for identity.
- Make the pet-scoped Library view read as one thing — pending recommendations and confirmed
  photos both clustered, both selectable — rather than two visually different screens bolted
  together.

## Non-goals

- Reopening or changing v1.8's pending-recommendation workflow (`ClusterPanel`, approve/reject/
  reassign-from-pending). That surface is unchanged; this spec adds a second, analogous one for
  already-confirmed photos.
- Changing `GET /api/library`'s existing query semantics, filters, or pagination for the flat
  "All photos" view (no pet selected). That view is untouched.
- Re-running or changing classification policy, thresholds, or the embedding model.
- Undoing a move. A move is an ordinary correction and gets the same "correct again" remedy any
  correction has today — no dedicated undo.
- A single unified endpoint for pending and confirmed clustering. They read from different pools
  (unreviewed vs. reviewed-and-confirmed-for-this-pet) with different skip semantics; the
  implementation may share the clustering primitive without sharing the pool query.

## Requirements

- **FR-1 — Cluster a pet's confirmed photos.** For the selected pet, cluster the crops already
  confirmed as that pet (i.e. `CropClassification` rows naming this pet's identity with an
  existing `ReviewAction`, or written by a prior cluster approval — the confirmed counterpart of
  `RecommendationClusterService`'s pending pool) using the same agglomerative-over-cosine-distance
  approach. Each cluster reports a representative crop, member count, confidence range (this
  pet's recorded confidence, not a top candidate's), and capture-date range. A crop with no stored
  embedding is excluded from clustering and reported as excluded, exactly as FR-2/FR-3 of v1.8
  handle it. This is a read; it writes nothing and does not touch `policy.py`.
- **FR-2 — Move a selection to a different pet.** Within the confirmed view, every photo in a
  cluster can be individually selected/deselected (`useSelection`), and a cluster or an arbitrary
  selection of confirmed photos can be moved to a different active pet of the same species in one
  action. The move applies to exactly the submitted ids — the server never re-derives cluster
  membership — and is validated against the pool that actually produced them, refusing (with a
  reason) an id that isn't a confirmed photo of the pet the request claims it's moving from. Each
  moved photo becomes one ordinary correction via `ClassificationCorrectionService.correct()`
  (same provenance as v1.8's `reassignCluster`), and the response reports applied/skipped counts
  with a reason per skip.
- **FR-3 — Sort.** The confirmed cluster view supports the same sort orders v1.8's FR-5 gave the
  pending view: capture date (oldest/newest first) and confidence (surest/least sure first).
- **FR-4 — One coherent pet-scoped view.** The pending-recommendations panel and the new confirmed
  view sit together on the pet-scoped Library page, visually distinguished (pending vs. confirmed
  is a real state difference the owner needs to see) but built from the same cluster-card and
  selection components, not a second visual language.
- Cross-species moves are rejected, matching v1.8 FR-10's merge rule and DT-1110's per-species
  identity uniqueness.
- A pet with no confirmed photos yet shows a plain empty state, not an error.

## Acceptance criteria

- Selecting a pet with confirmed photos shows them grouped into clusters with a representative
  crop, member count, confidence range, and capture-date range; a pet with none shows an explicit
  empty state; crops with no embedding are excluded and reported, not dropped silently.
- Every cluster member can be selected and deselected; select-all/select-none work within a
  cluster; moving a selection of N photos to a different pet produces N ordinary corrections with
  normal `ReviewAction`/provenance, reports applied/skipped counts with reasons, and changes no
  Immich state until the next operator-triggered sync.
- The server validates a move against the actual confirmed-pool membership; an id that isn't a
  confirmed photo of the claimed source pet is refused with a reason, not silently applied.
- A cross-species move is rejected with a clear error.
- Sort works the same four ways v1.8's pending view already supports.
- `GET /api/library`'s flat, no-pet-selected view and v1.8's pending-recommendation workflow are
  both unchanged; Vitest/pytest cover the new pool query, the selection/move flow, and the
  cross-species and stale-id rejection cases.

## Open questions

- Whether a move originating from the confirmed view should also let the owner reject to
  "no pet" (mirroring v1.8 FR-6) rather than only reassigning to a specific different pet, or
  whether that stays a pending-queue-only concept. Left for implementation-time discussion on the
  tracking issue rather than blocking the spec.

## Status

Implemented ([#183](https://github.com/bradreimer/immich-dog-tagger/issues/183)):
`ConfirmedClusterService` (a `RecommendationClusterService` subclass overriding only the pool
query) clusters a pet's confirmed photos; `ClusterApprovalService.move()` moves a selection to a
different pet as ordinary corrections, refusing anything not actually confirmed for the claimed
source pet. New `GET /library/clusters/confirmed` and `POST /library/clusters/move`; a new
Library panel reuses `ClusterCard` with approve/reject omitted and the reassignment control
relabeled "Move". FR-6-style rejection from the confirmed view (the Open question above) was not
built -- out of scope for this pass, left open.
