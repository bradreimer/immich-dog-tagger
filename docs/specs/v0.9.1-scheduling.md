# v0.9.1 Scheduling & Automation

## Goal

Make Immich Dog Tagger capable of operating unattended while keeping Mission Control as the place where schedules and automation are configured and observed.

The scheduler creates persistent PipelineJob records and delegates execution to the existing v0.9.0 job runner. It must not become a second implementation of the ML pipeline.

## Scope

- Persistent schedule definitions in `state.db`
- Scheduler lifecycle and due-occurrence evaluation
- Scheduled execution through the existing job runner
- FastAPI schedule management
- Mission Control schedule management
- Routine unattended automation
- Restart safety, concurrency protection, and observability

## Work breakdown

Work is broken down in `docs/tickets` in tickets DT-0911 through DT-0917.

## Scheduling model

A schedule has:

- stable ID
- human-readable name
- operation
- schedule expression
- explicit timezone semantics
- enabled/disabled state
- created/updated timestamps
- next-run information
- last-run information
- last-run result

Each scheduled occurrence must be uniquely identifiable so scheduler restarts cannot create duplicate jobs.

## Runtime model

```text
Mission Control
   ├── manual operation ──┐
   └── schedule ──────────┤
                          ▼
                     PipelineJob
                          ▼
                      Job Runner
                          ▼
                       state.db
```

The browser must not be required for scheduled execution.

## Mission Control

Provide a Schedules view showing:

- name
- operation
- schedule
- timezone
- enabled/disabled
- next run
- last run
- last result
- current queued/running state where useful

Controls:

- create
- edit
- enable/disable
- run now
- delete/archive if appropriate

Run Now creates a manual job and does not advance the schedule.

## Safety

The scheduler must:

- prevent duplicate occurrences
- respect existing job conflict/concurrency rules
- survive application restarts
- isolate individual job failures
- keep disabled schedules disabled
- never silently perform destructive Immich operations

A missed-occurrence policy must be explicit and documented during implementation.

## Routine automation

Use the existing pipeline/job operations. Prefer existing full-pipeline orchestration for routine new-photo processing.

Learning may be scheduled from accumulated review examples.

Immich sync may be scheduled using the existing safe sync implementation.

Do not introduce duplicate pipeline orchestration.

## Non-goals

- notifications
- multi-user authentication
- distributed workers
- cloud scheduling
- arbitrary scripts
- workflow designer
- new ML models or classification algorithms
- external task queues without a demonstrated need

## Exit criteria

- Schedules persist in `state.db`
- Scheduler runs with browser closed
- Due schedules create normal persistent jobs
- Existing job runner executes scheduled jobs
- Duplicate occurrences are prevented
- Conflicting work is handled safely
- Job failures do not stop unrelated schedules
- Mission Control manages schedules
- Run Now works
- Restart preserves schedules
- Scheduler health/failures are observable
- Recommended unattended operation is documented
- `./scripts/check.sh` passes
