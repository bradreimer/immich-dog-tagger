# v0.9.2 Data Safety & Recovery

## Goal

Make the production system safe to operate continuously against a real Immich library.

v0.9.0 established production deployment and Mission Control job infrastructure.
v0.9.1 adds unattended scheduling.

v0.9.2 closes the remaining operational safety gap:

> If the application, container, database, cache, host, or an operation fails, the user must have a clear and tested path to understand what happened and recover without losing the authoritative state.

## Core principle

`state.db` remains the source of truth.

Anything derived from Immich assets, downloaded files, crops, embeddings, classifications, or jobs must be recoverable or safely rebuildable from authoritative inputs.

## Scope

1. Explicit state database backup.
2. State database restore and validation.
3. Cache/derived-data lifecycle and rebuild behavior.
4. Job recovery and interrupted-operation handling.
5. Mission Control operational diagnostics.
6. Documented disaster-recovery procedure validated against the production deployment.

## Database safety

The backup mechanism must:

- produce a consistent SQLite backup
- preserve the database without requiring application shutdown where practical
- identify backup creation time
- avoid overwriting a known-good backup accidentally
- fail loudly when a backup cannot be completed
- be usable from the CLI and/or Mission Control

The implementation must use SQLite-aware backup semantics rather than copying a live database file blindly.

## Restore

Restore must be an explicit operation.

Before replacing the active database:

- validate the backup
- verify it is a readable SQLite database
- preserve the current database as a rollback point
- stop or coordinate with writers safely
- make the resulting state available to the application

The application must never silently restore a backup.

## Derived data

Derived artifacts include things such as:

- downloaded assets
- dog crops
- embeddings
- model outputs
- other cache files

The system must clearly distinguish authoritative state from rebuildable data.

Deleting rebuildable data must not corrupt `state.db`.

The system must provide a documented way to rebuild missing derived artifacts.

## Job recovery

Interrupted jobs must not leave the system believing work completed when it did not.

The recovery model should use the existing PipelineJob state machine.

On restart:

- identify jobs left in an active state
- determine whether they can safely resume
- otherwise mark them recoverable/failed according to existing semantics
- allow the user to retry them from Mission Control
- never silently duplicate destructive operations

The exact recovery behavior should follow the actual v0.9.0/v0.9.1 job implementation rather than introducing a second state machine.

## Mission Control diagnostics

Mission Control should provide enough information to answer:

- Is the application healthy?
- Is the scheduler healthy?
- What jobs are running or stuck?
- What failed recently?
- When was the last backup?
- Is the database healthy?
- Are derived artifacts missing?
- Is manual recovery required?

Do not build a monitoring platform. Provide focused operational visibility.

## Production validation

The release must include a repeatable recovery test against a disposable copy of production state.

The test must demonstrate:

1. create state
2. back it up
3. simulate failure/data loss
4. restore
5. validate state
6. resume operations
7. verify that review history and learned examples remain intact

Do not perform destructive experiments against the only copy of the real library.

## Non-goals

Do not add:

- cloud backup
- remote backup providers
- multi-host replication
- database clustering
- distributed workers
- new ML features
- notification integrations
- user authentication
- a general-purpose monitoring system

## Exit criteria

- A consistent `state.db` backup can be created.
- A backup can be validated.
- Restore is documented and tested.
- Restore creates a rollback point.
- Derived data can be safely rebuilt.
- Interrupted jobs have a defined recovery path.
- Mission Control exposes actionable operational diagnostics.
- A production-style recovery drill passes.
- No known path silently loses authoritative state.
- `./scripts/check.sh` passes.
