# v1.8.0 — Library as an Approval Workspace

Tracking issue: [#139](https://github.com/bradreimer/immich-dog-tagger/issues/139).

> **Status of this document.** v1.8's requirements are numbered here so every sub-issue has a
> stable reference. Requirements are specified in full as their sub-issue is picked up; until
> then the requirement line plus its sub-issue is the specification. FR-8 is specified in full
> below ([#146](https://github.com/bradreimer/immich-dog-tagger/issues/146)).

## Purpose

The Library is a flat, photo-first grid: every classified crop in one paginated list, corrected
one card at a time. Labeling cost therefore scales with the number of *photos*, not the number of
*pets*. The competitive analysis of our library workflow recorded in
[#139](https://github.com/bradreimer/immich-dog-tagger/issues/139) found
that Lightroom Classic, Immich, and Apple Photos all work the other way round — pick a subject,
then confirm a *group* of proposed photos in one action — and that the same analysis surfaced
adjacent gaps: no negative signal, no merge, no rescue for missed detections, and metrics that
never measure coverage.

v1.8 turns the Library into an identity-first approval workspace: select a species, select a pet,
then approve clusters of recommendations for that pet.

## User story

As the owner of a photo library, I want to settle many photos of one pet in a single decision, and
I want the numbers on the Metrics tab to tell me whether my *library* is tagged rather than only
how confidently the crops detection happened to find were labeled.

## Goals

- Make one human action settle a group of photos rather than a single photo.
- Keep every approval an ordinary correction with ordinary provenance — no new kind of state.
- Report coverage of the library honestly, including the photos that produced nothing.

## Non-goals

- Removing or changing the review queue.
- Any change to classification policy, thresholds, or the embedding model.
- Clustering that writes a prediction, manufactures a confidence value, or assigns an identity
  without a human action.
- Any change to detection itself.

## FR-8 — Detection coverage

### Problem

Every denominator in `services/metrics.py` counts `CropClassification` rows — photos where
detection already succeeded. Confident coverage, automation rate, and the per-species breakdown all
answer "of the crops we made, how many did we classify well". None of them can see a pet YOLO never
detected, so the Metrics tab can read 95% while a large share of the owner's real pet photos were
never in the funnel.

### Denominator (resolved open question)

**The denominator is photos detection has finished with**, i.e. assets whose status is `DETECTED`,
`CLASSIFIED`, `TAGGED`, or `CLASSIFICATION_FAILED` (the last three only occur in older databases;
`CLASSIFICATION_FAILED` still means detection itself completed). The alternatives were weighed as
follows:

- **Every scanned asset** — moves with pipeline backlog rather than detection outcome: a freshly
  scanned library reads 0% coverage while nothing has gone wrong.
- **Assets with at least one detection** — circular. It is the population that already succeeded,
  which is the exact blind spot FR-8 exists to remove.
- **Assets Immich tagged with a pet-ish label** — imports Immich's own model as ground truth, and
  ADR-001 makes Immich a photo source, not an authority on application state.

Assets still queued (`PENDING`, `DOWNLOADED`) and assets that cannot reach detection
(`DOWNLOAD_FAILED`, `DETECTION_FAILED`, `UNSUPPORTED`) are reported as their own counts rather than
folded into the denominator, so a backlog or a run of failures is visible as itself instead of
depressing the coverage figure.

### Requirements

- **FR-8.1** — The Metrics tab shows what share of the photos detection has finished with produced
  at least one pet crop, with the denominator stated in plain language beside the figure.
- **FR-8.2** — Photos that produced no crop are shown as their own count. That is the population a
  missed pet hides in, and it is the entry point for FR-11's rescue path.
- **FR-8.3** — Photos awaiting detection, and photos that could not be processed, are reported
  separately from both the numerator and the denominator.
- **FR-8.4** — The existing automation-rate, confident-coverage, review-rate, and per-species
  figures keep their current definitions and values. FR-8 adds numbers; it redefines none.
- **FR-8.5** — Wording never claims accuracy, recall, or a probability. There is no labeled ground
  truth for photos detection never flagged, so this is coverage and must read as coverage —
  the same discipline as the "no calibrated probabilities" rule in
  [docs/workflow.md §4](../workflow.md).
- **FR-8.6** — Before detection has processed anything, the share is reported as absent rather
  than as 0%, which would read as "detection found nothing".
- **FR-8.7** — Reuses the existing stat-tile primitive; no new visual language.

### Acceptance criteria

- `GET /metrics` returns the photo-denominated counts alongside the existing crop-denominated ones.
- Metrics service tests cover a fixture with assets in every status, including assets with zero
  detections, and assert both the coverage figure and the no-crop count.
- A regression test pins the automation rate so this change cannot shift it.
- A query-count assertion pins the metrics endpoint to a fixed number of queries as the library
  grows — no N+1 or per-asset query at library scale.

### Out of scope

- A dry-run classification accuracy tool.
- Per-identity precision/recall reporting — see
  [reference-example-management.md](reference-example-management.md).
