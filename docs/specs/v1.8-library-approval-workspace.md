# v1.8 — Library as an Approval Workspace

Tracking feature: [#139](https://github.com/bradreimer/immich-dog-tagger/issues/139).

## Purpose

Turn the Library from a flat, photo-first grid into an identity-first approval workspace:
select a species, select a pet, then approve clusters of recommendations for that pet.
Labeling cost should scale with the number of **pets**, not the number of **photos**.

This spec is the shared home for the v1.8 requirements. Each requirement is implemented by its
own issue; a requirement is written out in full here once its issue is being implemented, and
stays a one-line summary until then.

## User story

As the owner, I want to work one pet at a time and settle many photos per decision, so that
tagging my library is a bounded amount of work rather than one interaction per photo.

## Goals

- One decision settles a group of photos, not a single photo.
- The owner's entry point is a pet, not a page of unrelated crops.
- Duplicate and misspelled identities are recoverable rather than permanent.
- Coverage is reported honestly, including photos the detector never produced a crop for.

## Non-goals

- The `/review` queue is not removed or changed.
- No change to classification policy, thresholds, or the embedding model as part of the core
  workflow change.
- Clustering proposes **groupings only**: it never writes a prediction, never manufactures a
  confidence value, and never assigns an identity without a human action.
- Splitting an identity (the inverse of FR-10) is not in scope.
- Automatic duplicate detection or merge suggestions are not in scope.

### FR-10 — Merge two identities

The owner can merge a source identity into a target identity. Naming clusters (FR-2/FR-7) makes
near-duplicate identities ("Fibs", "Fibsy") easy to create, and today the only remedy is
deactivation, which hides the duplicate while stranding its classifications, its reference
examples, and its Immich album.

FR-10.1 — `DogService.merge_dogs(source_id, target_id)` reassigns every `CropClassification`
attributed to the source (scoped to crops of the merged species, since `identity` is a name and
names are unique *per species*) to the target's name, and re-files the source's
`EmbeddingExample` rows onto the target.

FR-10.2 — Both identities must be the **same species**. A dog and a cat sharing a name are two
legitimately different identities (the collision DT-1110 fixed in album naming); a cross-species
merge is rejected with a clear error, never silently coerced.

FR-10.3 — Review history is never rewritten. `ReviewAction` rows keep the identity strings the
human actually chose at the time; a merge is a bulk re-attribution of *derived* state, not a
rewrite of the record of who decided what.

FR-10.4 — A crop path can only depict one animal, so a source example whose `crop_path` the
target already has is discarded rather than duplicated — the same invariant `Learner` maintains.

FR-10.5 — `PetOccurrence` rows (derived facts, ADR-004) for the source are re-pointed at the
target so insights follow the merge.

FR-10.6 — Album reconciliation rides the existing DT-1113 `SyncedAsset` machinery: because the
classifications now name the target, the next `SyncService.sync()` sees the source's membership
as stale and removes it, rather than leaving photos in both albums forever.

FR-10.7 — The merge is recorded in an `identity_merges` provenance table (source id/name, target
id/name, species, counts, timestamp). `state.db` holds history that cannot be regenerated, and a
merge is a bulk rewrite of identity attribution that must be traceable afterward.

FR-10.8 — The source identity is kept as a deactivated tombstone rather than deleted. This is
consistent with how the app already avoids destructive edits, and it keeps the provenance row's
foreign keys resolvable.

FR-10.9 — Writes are batched and committed incrementally. Merging a well-populated identity
touches every one of its classifications; a single long write transaction is the lock-contention
problem #104/#107 already fixed elsewhere.

FR-10.10 — In the UI the action is styled as destructive and confirmed before it runs, per
[ux-principles.md](ux-principles.md).

## Acceptance criteria

FR-10:

- Two same-species identities can be merged; every classification and reference example from the
  source ends up under the target.
- Merging across species is rejected with a clear error.
- Review history survives the merge.
- After the next sync, merged photos are in the target's album and no longer in the source's.
- The merge is recorded so it can be traced later.
- Merging an identity with many classifications commits in batches and does not hold a long write
  lock.
- The action is styled as destructive and confirmed before it runs.
- A merge followed by Reclassify does not resurrect the source identity on any crop.

Acceptance criteria for the other requirements live on their issues until those requirements are
written out here.
