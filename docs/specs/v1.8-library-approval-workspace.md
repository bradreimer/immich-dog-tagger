# v1.8 Library as an approval workspace

Competitive context: [docs/competitive-analysis-library-workflow.md](../competitive-analysis-library-workflow.md).

## Purpose

Today the Library is a flat, photo-first grid: every classified crop in one paginated list,
filtered by identity/species/reviewed-status/date, corrected one card at a time through a
per-card dropdown. It is a good browsing surface and a poor working surface — the owner's
labeling cost scales with the number of *photos*, not the number of *pets*.

Every comparable faces workflow (Lightroom Classic, Immich, Apple Photos) works the other way
round: pick a subject, then confirm a *group* of proposed photos in one action. This spec turns
the Library into that surface — **choose a species, choose a pet, approve clusters of
recommendations** — while keeping the existing filtered grid available underneath it.

This is a UX and workflow change on top of the existing pipeline. Detection, embedding,
classification policy, and Reclassify semantics are unchanged; a cluster approval writes exactly
the same ground truth a single correction writes today.

## User story

As the owner, I want to pick a species and a pet, see the photos the system thinks are that pet
grouped into clusters, sort those results by capture date or confidence, and approve or reject a
whole cluster in one action, so that tagging a pet takes a handful of decisions instead of one
decision per photo.

## Goals

- Make the Library **identity-first**: species → pet → that pet's pending recommendations.
- Group recommendations into **clusters of visually similar crops** so one approval settles many
  photos.
- Let the owner **sort** clusters and the photos inside them by capture date (oldest→newest,
  newest→oldest) or by confidence.
- Let the owner **exclude individual photos** from a cluster before approving it, so one click
  never writes bad ground truth at scale.
- Let the owner **reject** a recommendation as "not this pet" and have that be a real signal, not
  a silent no-op.
- Give a pet with **no examples yet** a usable starting point, so the first session does not
  require 50–100 unassisted single-item reviews.
- Keep every approval indistinguishable, in the data model, from a correction made today:
  ground truth with provenance, feeding the same reference set.

## Non-goals

- **The review queue is not removed or changed.** It remains the triage view for "what most needs
  attention right now" ([v1.4 spec](v1.4-trustworthy-photo-library.md) non-goals; unchanged here).
- **No change to classification policy, thresholds, or the embedding model** as part of the core
  workflow change. Owner-facing sensitivity is a separate, explicitly lower-priority requirement
  (FR-9) and must route through `policy.py`, never a new threshold literal.
- **No new detection or embedding work.** Clustering runs over `CropClassification.embedding`,
  which already exists for classified crops.
- **No cluster identity inference.** Clustering proposes *groupings* only. It never writes a
  prediction, never manufactures a confidence value, and never assigns an identity without a
  human action — consistent with the v1.0.0 "no manufactured confidence" rule.
- **No undo/redo system.** A mistaken approval is fixed the way every other mistake is fixed: by
  correcting it again (v1.4 non-goal, unchanged).
- **No bulk species correction.** Out of scope here, as in
  [species-correction.md](species-correction.md).

## Requirements

### FR-1: Species → pet selection as the Library's primary axis

The Library opens on a pet chooser: species (Dog / Cat / All) and then a named identity. Selecting
a pet scopes everything below it to that pet. The existing filters (review status, capture-date
range) and the flat grid remain available as a secondary "all photos" view, so nothing that works
today is lost.

Reuses `GET /api/dogs` and the existing `library` query in `ReviewQueryService`.

### FR-2: Recommendation clusters for the selected pet

For the selected pet, the app assembles a **candidate pool**: unreviewed classifications of the
matching species whose predicted identity is that pet, or that list that pet among
`CropClassification.candidates`. The pool is clustered by visual similarity over the stored
`CropClassification.embedding` values (no re-embedding, no new pipeline stage), and each cluster
is presented with a representative crop, a member count, a confidence range, and a capture-date
range.

Clustering is a read-side operation. It must not write predictions, confidences, or identities.

### FR-3: Approve a cluster in one action

Approving a cluster assigns the selected pet to every included member, via the existing
`ClassificationCorrectionService` path used by `POST /classifications/{id}/correct` — the same
`ReviewAction` rows, the same `EmbeddingExample` creation, the same provenance, the same
stale-album reconciliation on the next sync (DT-1113). A cluster approval is N ordinary
corrections, not a new kind of state.

The response reports how many members were assigned and how many were skipped and why, following
the accounting convention #1117 established for sync.

### FR-4: Per-photo exclusion before approval

Every cluster member can be deselected before the cluster is approved, and the approve action
applies only to the selected members. A cluster is never all-or-nothing — an impure cluster with
one wrong photo must be approvable without writing that wrong photo as ground truth.

### FR-5: Sort by capture date or confidence

Both the cluster list and the photos within a cluster can be sorted by:

- **Capture date, oldest first**
- **Capture date, newest first**
- **Confidence** (highest first, and lowest first)

Sorting is server-side and works with pagination — an offset into a differently-sorted result set
must not skip or repeat items. Photos with no `captured_at` sort last under both date orders
rather than being hidden. The default is confidence, highest first (approve the surest group
first).

### FR-6: Reject a recommendation as "not this pet"

A cluster or an individual member can be rejected for the selected pet. A rejection records that
this crop is not that identity and suppresses that identity as a candidate for that crop on
subsequent classification passes. It does not assign an identity, and it does not mark the crop
reviewed for the purpose of the review queue unless the crop's identity is otherwise settled —
rejecting "not Hermann" leaves "who is it?" open.

This is a new signal, and it needs an explicit decision (see Open questions) about how it
interacts with "a human review is authoritative input."

### FR-7: A usable start for a pet with no examples

When the selected pet has no reference examples, the candidate pool from FR-2 is empty. In that
state the workspace instead shows clusters of **unlabeled crops of the matching species** — the
same clustering over the same embeddings, with no identity attached — so the owner can name a
cluster as that pet and bootstrap the reference set in one action instead of 50–100 single-item
reviews.

Approval semantics are identical to FR-3/FR-4.

### FR-8: Honest coverage reporting

The Metrics surfaces today count only `CropClassification` rows — photos where detection already
succeeded — so automation rate can read very high while a large share of the library was never
detected at all. Add a coverage figure with a stated, defensible denominator, and surface photos
that produced no crop as a visible category rather than an absence.

### FR-9: Owner-facing tagging sensitivity, and reclassify after review

Two smaller follow-ups, deliberately last:

- A single owner-facing "how cautious should automatic tagging be" control, mapped to the existing
  `policy.py` threshold — one policy, no new literals.
- Automatically run Reclassify after a review or approval batch settles, so the owner sees the
  effect of their work without knowing to click a button.

### FR-10: Identity hygiene — merge

Two identities can be merged: classifications reassigned, embedding examples re-filed, provenance
recorded, and album membership reconciled on the next sync through the existing DT-1113
machinery. Today `DogService` offers create/rename/activate only, so a duplicate or misspelled pet
can be deactivated but never reconciled.

### FR-11: Rescue a pet the detector missed

If YOLO produced no crop for a photo, that photo is invisible to the entire system. Provide a
minimal path to mark that an asset contains a given pet — enough to create a reference example and
make the photo album-eligible — without building a full manual region editor.

## Acceptance criteria

- Selecting Dog → "Fibs" scopes the Library to Fibs and shows clusters of pending
  recommendations for Fibs, with a representative crop, member count, confidence range, and
  capture-date range per cluster.
- Approving a cluster of N members creates N review actions and N reference examples, identical in
  shape to N single corrections, and reports the counts it applied and skipped.
- Deselecting members before approving applies the approval only to the remaining members.
- Cluster lists and cluster members can each be sorted by capture date (both directions) and by
  confidence (both directions); results paginate correctly under every sort order, and undated
  photos appear last rather than disappearing.
- Rejecting a member for the selected pet suppresses that identity for that crop on the next
  classification pass and does not assign an identity.
- Selecting a pet with zero examples shows unlabeled clusters of the matching species, and naming
  one seeds that pet's reference set.
- Reclassify remains idempotent and still never mutates a reviewed label after any of the above.
- The existing review queue, its keyboard flow, and the flat library grid all still work.

## Open questions

- **Clustering algorithm and where it runs.** Immich uses DBSCAN over face embeddings; agglomerative
  clustering over cosine distance is the other obvious candidate for a library this size. Does
  clustering run on demand per request (simpler, no new state, cost scales with pool size) or as a
  job with cached cluster assignments (faster UI, new state to invalidate)? On-demand is the
  smaller first cut if the candidate pool stays bounded per pet.
- **Does a rejection (FR-6) belong in `ReviewAction`** as a new action type, or in its own table?
  A new action type is smaller but changes what "reviewed" means for every count that derives from
  `ReviewAction` — exactly the class of subtle breakage #1115 and #116 already ran into.
- **What is the honest denominator for coverage (FR-8)** in a library where most photos legitimately
  contain no pets?
- **Should approvals sync immediately** or wait for the next sync run? Approving 200 photos at once
  makes the delay between "I approved it" and "it's in the album" much more visible than a single
  correction did.
- **Should confirmed pets also be written to Immich's People surface**, not only albums? The
  directly competing sidecar does this and it is better for search, but it means writing into a
  namespace Immich owns. This needs an ADR, not a patch, and is deliberately out of scope here.
