# v1.8.0 — Library as an Approval Workspace

Tracking issue: [#139](https://github.com/bradreimer/immich-dog-tagger/issues/139).

## Purpose

The Library today is a flat, photo-first grid: every classified crop in one paginated list,
corrected one card at a time through a per-card dropdown (`ui/src/features/library/LibraryPage.tsx`,
`components/LibraryEntryCard.tsx`). It browses well and works badly — labeling cost scales with the
number of **photos**, not the number of **pets**, and the maximum confirmation rate anywhere in the
app is one photo per interaction.

Every comparable faces workflow (Lightroom Classic, Immich, Apple Photos) works the other way
round: pick a subject, then confirm a **group** of proposed photos in one action. This spec turns
the Library into an identity-first approval workspace — **select a species → select a dog or cat →
approve clusters of recommendations for that pet** — sortable by capture date or confidence.

Clustering runs over `CropClassification.embedding`, which already exists for classified crops: no
new model, no new pipeline stage, no change to classification policy. A cluster approval routes
through the existing `ClassificationCorrectionService`, so it is N ordinary corrections with
ordinary provenance, not a new kind of state.

## User story

As the owner of a large library,
I want to pick one of my pets and confirm a whole group of proposed photos in a single action,
so that the work I do scales with how many pets I have rather than with how many photos they
appear in.

## Goals

- Make the **subject** the primary axis of the Library: species and pet are a selection step, not
  two filters among four.
- Let one human decision settle many photos, by proposing clusters of visually similar
  recommendations for the selected pet and approving a cluster in one action.
- Keep every approval an ordinary correction: same service, same provenance, same learning
  examples. Clustering proposes **groupings only** — it never writes a prediction, never
  manufactures a confidence value, and never assigns an identity without a human action.
- Close the supporting gaps the same analysis found: no negative signal (rejection), no identity
  merge, no rescue for a photo the detector missed, and coverage that is never measured.

## Non-goals

- Removing or changing the review queue. `/review` stays exactly as it is.
- Changing classification policy, thresholds, or the embedding model as part of the core workflow
  change.
- Changing `GET /api/library`'s query semantics.
- A fully automatic, Apple-style model that labels without the owner. Operator controls, jobs, and
  diagnostics are a differentiator for a self-hosting owner, not debt.
- **Cold-start clustering.** Bootstrapping a pet with no reference examples stays the Review tab's
  job: with zero examples every crop has `identity IS NULL`, and `active_review()` already sorts
  exactly those first, so the existing single-item keyboard flow covers it. This applies to a pet
  added later too — a new arrival years into a library has no examples, so it has no clusters, and
  is bootstrapped through Review. Decided in review; FR-7 dropped and
  [#145](https://github.com/bradreimer/immich-dog-tagger/issues/145) closed as not planned.
- **Approving does not sync to Immich.** An approval settles identity in `state.db` and nothing
  more; album membership is reconciled on the next operator-triggered sync, exactly as a single
  correction behaves today. This is the general rule in
  [ADR-006](../adr/ADR-006-immich-operations-explicit-local-operations-on-demand.md), not a one-off:
  anything touching Immich runs only when the operator asks or on a schedule they configured, while
  local-only work may be triggered automatically and appears in the job queue when long-running.

## Requirements

Each requirement is tracked as its own issue. Core workflow, in dependency order:

- **FR-1 — Library scoped to one pet** ([#140](https://github.com/bradreimer/immich-dog-tagger/issues/140)).
  The Library opens on a species (Dog / Cat / All) and pet selection, and everything it shows is
  scoped to that selection. Detailed below.
- **FR-2 / FR-3 — Cluster and approve** ([#141](https://github.com/bradreimer/immich-dog-tagger/issues/141)).
  Cluster the recommendations for the selected pet over the existing crop embeddings, and approve a
  whole cluster in one action via `ClassificationCorrectionService`. Clustering is **agglomerative
  over cosine distance, computed on demand** as a request-scoped read, and approval is a
  **synchronous write, not a job** (see Resolved decisions). An approval writes state only and never
  triggers a sync.
- **FR-4 — Refine a cluster before approving** ([#142](https://github.com/bradreimer/immich-dog-tagger/issues/142)).
  Select and deselect individual photos within a proposed cluster.
- **FR-5 — Sorting** ([#143](https://github.com/bradreimer/immich-dog-tagger/issues/143)).
  Sort clusters and photos by capture date (oldest→newest, newest→oldest) or by confidence.
- **FR-6 — Rejection** ([#144](https://github.com/bradreimer/immich-dog-tagger/issues/144)).
  Reject a recommendation as "not this pet" — the negative signal the workflow has never had.
  Stored in **its own table**, not as a new `ReviewActions` value (see Resolved decisions).
- **FR-7 — Cold start** — **dropped.** Originally: cluster unlabeled crops for a pet with no
  examples yet. Not built; the Review tab already serves the zero-example case (see Non-goals).
  [#145](https://github.com/bradreimer/immich-dog-tagger/issues/145) is closed as not planned.
  Numbering is left stable so FR-8 → #146, FR-9 → #149, FR-10 → #148 and FR-11 → #147 keep
  resolving.
- **FR-8 — Honest coverage** ([#146](https://github.com/bradreimer/immich-dog-tagger/issues/146)).
  Report detection coverage, not just automation rate over already-detected crops.
- **FR-9 — Sensitivity and follow-up reclassification** ([#149](https://github.com/bradreimer/immich-dog-tagger/issues/149)).
  Owner-facing tagging sensitivity, and reclassify automatically after a review batch.
- **FR-10 — Merge identities** ([#148](https://github.com/bradreimer/immich-dog-tagger/issues/148)).
  Merge a duplicate or misspelled identity into another. Detailed below.
- **FR-11 — Rescue a missed detection** ([#147](https://github.com/bradreimer/immich-dog-tagger/issues/147)).
  Tag a photo whose pet the detector missed.

### FR-1 in detail

FR-1 is the information-architecture half of the feature: it ships no clustering and no bulk
action, it builds the surface the rest land on.

1. The Library presents a species chooser (Dog / Cat / All) and, within the chosen species, a pet
   chooser listing the active identities from `getDogs({ includeInactive: false })`.
2. Selecting a pet scopes the photos shown to that pet and that species, via the `identity` and
   `species` parameters `GET /api/library` already accepts. No new endpoint.
3. The flat "all photos" view remains reachable as an explicit choice alongside the pets, and its
   review-status filter, capture-date filters, and pagination keep working exactly as they do
   today.
4. Changing species clears a pet selection that no longer applies, rather than leaving a dog
   selected under Cats.
5. Changing any selection resets pagination — the existing offset-reset behavior must not regress.
6. A library with no identities configured shows a clear empty state pointing at Dogs & Cats, not
   a blank chooser.
7. The selection is workspace state that the later requirements read from, not state local to a
   filter row.

### FR-2 / FR-3 in detail

FR-2/FR-3 are the workflow half of the feature: with the pet selected (FR-1), the Library proposes
groups of that pet's pending recommendations and settles a whole group in one action.

1. The **candidate pool** for pet X is the unreviewed `CropClassification` rows whose crop species
   matches X's species and where X is either the accepted `identity` or one of the stored
   `candidates`. It is always identity-scoped and never the whole unlabeled library (see "Resolved
   decisions": cold start is out), so the pool is bounded by how much work X actually has pending.
2. Clustering runs **agglomerative over cosine distance, on demand**, over the embeddings already
   stored on those rows. It lives in a service, never in a route or the UI.
3. Clustering is **not classification**. It writes nothing -- no prediction, no confidence, no
   identity -- and it must not read or write `policy.py`'s thresholds. Running it twice with no
   approvals in between changes no rows.
4. Each cluster reports a representative crop, its member count, the confidence range, and the
   capture-date range. The confidence reported for a pet is *that pet's* similarity, never the top
   candidate's, so a crop where X is a runner-up does not read as a strong match for X.
5. A crop with a null `embedding` is excluded from clustering and reported as excluded, rather than
   crashing the pass or vanishing from the count.
6. **Approving** a cluster routes every member through `ClassificationCorrectionService.correct()`:
   an approval of N members is N ordinary corrections, with the same `ReviewAction` rows, the same
   `EmbeddingExample` creation, and the same provenance as N single corrections from `/review`.
7. The approve response reports how many members were assigned and how many were skipped, with a
   reason per skip (DT-1117's accounting convention -- a silent shortfall is a bug).
8. Both sides are bounded. The pool is capped, and a capped pool says so; an approval commits in
   batches so a failure partway leaves committed progress rather than a rolled-back hour.
9. Approving changes no Immich state. Album membership reconciles on the next operator-triggered
   sync, exactly as a single correction behaves today ([ADR-006](../adr/ADR-006-immich-operations-explicit-local-operations-on-demand.md)).

### FR-4 in detail

FR-4 is the correction half of FR-2/FR-3: clustering by visual similarity will produce impure
groups -- two similar-looking dogs, a bad crop, a different pet at the same angle -- and without
per-member control one approval either writes the wrong label at scale or has to be abandoned
whole, which throws away the throughput FR-3 exists to deliver.

1. Every member of a proposed cluster can be individually deselected and reselected, including the
   members a large cluster collapses behind a "show all" control.
2. **Members start selected.** Deselecting the odd photo out is the exception path, so the common
   case stays one click.
3. The approve control names the count it will apply to ("Approve 14 photos"), not just "Approve",
   and a visible count states how many of how many are selected.
4. Select-all and select-none work within a cluster.
5. Deselecting every member disables approve rather than submitting an empty approval, and an
   empty list is refused by the API and the service rather than treated as "approve the cluster".
6. Selection state is cleared when the selected pet or the cluster set changes. A selection is only
   meaningful against the list it was made over; a stale one must never carry across pets.
7. **The approval submits an explicit member list and the server never re-derives cluster
   membership from it.** Approving "the cluster" server-side would sweep back in exactly the photos
   the owner deselected, from a cluster the client may no longer be looking at.
8. The server validates the submitted ids against the same pool rule that produced the cluster
   (FR-2 point 1): an id the classifier never proposed this pet for is refused with a reason, not
   silently labelled. This is the boundary check, not a client courtesy -- a stale page or a
   hand-written request must not be able to write a label the owner never saw proposed.
9. Selection reuses the app's existing visual language -- the filled-vs-outline state the review
   filter buttons and #117's predicted-identity highlight already use, in the shared orange action
   color -- and adds no second keyboard vocabulary: members are real toggle controls, so the
   Review page's keymap (`useReviewKeyboard.ts`) stays the app's only one.
10. The selection primitive is generic over ids and lives outside the Library feature, since this is
    the app's first multi-select and the flat library grid is the next caller.

### FR-8 in detail

FR-8 is the measurement half of the feature: it changes no pipeline behavior, it makes the
Metrics tab able to see what detection never found.

**The problem.** Every denominator in `services/metrics.py` counts `CropClassification` rows —
photos where detection already succeeded. Confident coverage, automation rate, and the per-species
breakdown all answer "of the crops we made, how many did we classify well". None of them can see a
pet YOLO never detected, so the Metrics tab can read 95% while a large share of the owner's real
pet photos were never in the funnel.

**The denominator** (the open question this requirement had to settle) is **photos detection has
finished with**: assets whose status is `DETECTED`, `CLASSIFIED`, `TAGGED`, or
`CLASSIFICATION_FAILED`. Only `DETECTED` is written by the current pipeline; the other three occur
in older databases, and a classification failure still means detection itself completed. The
alternatives were weighed and rejected:

- *Every scanned asset* — moves with pipeline backlog rather than detection outcome. A freshly
  scanned library would read 0% coverage while nothing has gone wrong.
- *Assets with at least one detection* — circular. That is the population that already succeeded,
  which is the exact blind spot FR-8 exists to remove.
- *Assets Immich itself tagged with a pet-ish label* — imports Immich's model as ground truth, and
  [ADR-001](../adr/ADR-001-state-database-source-of-truth.md) makes Immich a photo source, not an
  authority on application state.

1. The Metrics tab shows what share of the photos detection has finished with produced at least one
   pet crop, with that denominator stated in plain language beside the figure.
2. Photos that produced **no crop** are shown as their own count. That is the population a missed
   pet hides in, and it is the entry point for FR-11's rescue path.
3. Photos awaiting detection (`PENDING`, `DOWNLOADED`) and photos that cannot reach it
   (`DOWNLOAD_FAILED`, `DETECTION_FAILED`, `UNSUPPORTED`) are reported separately from both the
   numerator and the denominator, so a backlog or a run of failures reads as itself instead of
   depressing coverage.
4. The existing automation-rate, confident-coverage, review-rate, and per-species figures keep
   their current definitions and values. FR-8 adds numbers; it redefines none — the #115 failure
   mode.
5. Wording never claims accuracy, recall, or a probability. There is no labeled ground truth for
   photos detection never flagged, so this is *coverage* and must read as coverage — the same
   discipline as the "no calibrated probabilities" rule in [docs/workflow.md §4](../workflow.md).
6. Before detection has processed anything, the share is reported as absent rather than as 0%,
   which would read as "detection found nothing".
7. Reuses the existing stat-tile primitive (DT-1104/DT-1105); no new visual language.
8. No N+1 or per-asset query: the counts are fixed aggregates regardless of library size.

### FR-10 in detail

Naming clusters (FR-2/FR-7) makes near-duplicate identities ("Fibs", "Fibsy") easy to create, and
today the only remedy is deactivation, which hides the duplicate while stranding its
classifications, its reference examples, and its Immich album.

1. `DogService.merge_dogs(source_id, target_id)` reassigns every `CropClassification` attributed to
   the source to the target's name, and re-files the source's `EmbeddingExample` rows onto the
   target.
2. The rewrite is scoped to crops of the merged species. `CropClassification.identity` is a bare
   name and names are unique *per species* (DT-1110), so merging the dog "Max" must leave the cat
   "Max"'s photos alone.
3. Both identities must be the **same species**. A dog and a cat sharing a name are two
   legitimately different identities; a cross-species merge is rejected with a clear error, never
   silently coerced.
4. Review history is never rewritten. `ReviewAction` rows keep the identity strings the human
   actually chose at the time — a merge re-attributes *derived* state, not the record of who
   decided what.
5. A crop path can only depict one animal, so a source example whose `crop_path` the target already
   holds is discarded rather than duplicated — the same invariant `Learner` maintains.
6. `PetOccurrence` rows (derived facts, ADR-004) for the source are re-pointed at the target so
   insights follow the merge.
7. Album reconciliation rides the existing DT-1113 `SyncedAsset` machinery: because the
   classifications now name the target, the next `SyncService.sync()` sees the source's membership
   as stale and removes it, rather than leaving photos in both albums forever. The merge
   deliberately leaves those rows alone so that diff can do its job.
8. The merge is recorded in an `identity_merges` provenance table (source and target ids and names,
   species, counts, timestamp). `state.db` holds history that cannot be regenerated (ADR-001), and a
   bulk re-attribution cannot be read back off the rows it touched.
9. The source identity is kept as a deactivated tombstone rather than deleted — consistent with how
   the app already avoids destructive edits, and it keeps the provenance row's foreign keys
   resolvable.
10. Writes are batched and committed incrementally. Merging a well-populated identity touches every
    one of its classifications; a single long write transaction is the lock-contention problem
    #104/#107 already fixed elsewhere.
11. In the UI the action is styled as destructive and confirmed before it runs, per
    [ux-principles.md](ux-principles.md).

Out of scope: splitting an identity (the inverse operation), and automatic duplicate detection or
merge suggestions.

## Acceptance criteria

- **FR-1**: the Library opens on a species and pet selection; selecting a pet scopes the grid;
  the flat all-photos view, its filters, and pagination still work; changing species clears a
  now-invalid pet; every selection change resets pagination; an identity-less library points the
  owner at Dogs & Cats. Vitest covers the species/identity invalidation, the pagination reset, and
  the empty-identities state.
- **FR-2/FR-3**: selecting a pet shows clusters of its pending recommendations, each with a
  representative crop, member count, confidence range, and capture-date range; approving a cluster
  of N recommendations produces N corrections through `ClassificationCorrectionService` with normal
  provenance, and no classification is written without a human action; the approve response reports
  the counts applied and skipped with reasons; clustering writes nothing and is deterministic for
  the same input; crops with a null embedding are excluded and reported rather than crashing the
  pass; a pet with no pending candidates shows an explicit empty state; reclassify after an approval
  stays idempotent and mutates no approved label; and approving changes no Immich state -- photos
  land in the right albums only after the next operator-triggered sync.
- **FR-4**: every cluster member can be deselected and reselected; the approve action applies to
  exactly the selected members and nothing else, verified server-side against the submitted list;
  the approve control shows the count it will apply to; select-all and select-none work within a
  cluster; deselecting every member disables approve rather than submitting an empty approval; and
  the selection is cleared when the pet or the cluster set changes. Vitest covers deselect ->
  approve submitting only the remaining ids, select-none disabling approve, and the reset on a pet
  change; service tests cover an approval naming ids outside the pet's recommendations being
  refused with a reason rather than silently applied.
- **FR-8**: `GET /metrics` returns the photo-denominated counts alongside the existing
  crop-denominated ones; the Metrics tab states the denominator next to the coverage figure and
  shows the no-crop photos as their own count. Metrics service tests cover a fixture with assets in
  every status, including assets with zero detections; a regression test pins the automation rate so
  this cannot shift it; a query-count assertion pins the metrics endpoint to a fixed number of
  queries as the library grows.
- **FR-10**: two same-species identities can be merged, and every classification and reference
  example from the source ends up under the target; a cross-species merge is rejected with a clear
  error; review history survives; after the next sync the merged photos are in the target's album
  and no longer in the source's; the merge is recorded so it can be traced later; a merge of an
  identity with many classifications commits in batches rather than holding one long write lock;
  a merge followed by Reclassify does not resurrect the source identity on any crop; and the UI
  action is styled as destructive and confirmed before it runs.
- Every requirement leaves `/review` and `GET /api/library`'s query semantics unchanged.

## Resolved decisions

- **Cold start stays with the Review tab.** FR-7 dropped, #145 closed as not planned. See
  Non-goals.
- **Approving does not sync.** Generalized into
  [ADR-006](../adr/ADR-006-immich-operations-explicit-local-operations-on-demand.md). See Non-goals.
- **Clustering is agglomerative over cosine distance, computed on demand.** DBSCAN — what Immich
  uses for faces — was the alternative; its advantage is noise handling over a large unlabeled pool,
  which stopped applying once cold start was dropped and the candidate pool became identity-scoped
  and bounded. Agglomerative gives a tunable distance cut in the same cosine space
  `SimilarityScorer` already works in, and on demand adds no cached cluster state to invalidate. The
  distance cut is a clustering knob, not a classification threshold: it must not live in or near
  `policy.py`. If measurement during #141 shows clustering is slow enough to feel like an operation,
  promoting it to a job with cached assignments is the remedy — decided by evidence, not up front.
  Measured during #141: a full 500-crop pool of 512-dimension embeddings clusters in ~0.3s
  (`tests/test_scale.py::test_clustering_a_full_pool_stays_interactive`), so it stayed a read.
- **Clustering stays a request-scoped read and cluster approval stays a synchronous write** —
  neither becomes a job. ADR-006's "long-running work appears in the job queue" rule is bounded by
  the job system's single-active-job constraint (`PipelineJobRunner._run()` raises when another job
  is running): an interactive approval routed through the queue would fail or block behind a running
  pipeline.
- **A rejection lives in its own table**, not as a new `ReviewActions` value.
  `review_queue_count()`, `_has_review_action()`, the library's `reviewed` flag and the Metrics
  reviewed counts all derive from the mere *existence* of a `ReviewAction`, so a new action type
  would make a rejected crop count as reviewed everywhere at once — the failure DT-1115 and #116
  already ran into. Costs a join; keeps "reviewed" meaning one thing.

## Open questions

- **FR-8's coverage shape is unreconciled.** #146 shipped a *share* over "photos detection has
  finished with", plus a separate no-crop count ("FR-8 in detail" above). A parallel review of this
  spec settled on **two plain counts and no ratio at all** — assets scanned, and assets with at
  least one pet detection — precisely to avoid having a denominator to defend. Both readings agree
  on the goal (make what detection never found visible) and disagree on the form. The shipped
  behavior is what "FR-8 in detail" documents; whether to keep it or change it to two plain counts
  is an open call for the owner, and a follow-up issue if it changes.
- **Should confirmed pets also be written to Immich's People surface**, not only albums? The
  directly competing sidecar does this and it is better for search, but it means writing into a
  namespace Immich owns. This needs an ADR, not a patch, and is out of scope here.
