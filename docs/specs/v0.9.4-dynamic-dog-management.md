# v0.9.4 Dynamic Dog Management

## Goal

Remove hard-coded dog names from the product and make dog identities fully user-managed through Mission Control.

A clean installation should start with no dogs configured. Operators should be able to add, edit, and remove dog identities through the web UI, and the rest of the learning/review pipeline should consume those records dynamically.

## Scope

v0.9.4 changes the identity experience from static, baked-in names to data-driven dog records.

The product must continue to support the existing operational loop:

```text
Immich
  ↓
scan
  ↓
detect
  ↓
crop
  ↓
embed
  ↓
classify
  ↓
Mission Control review
  ↓
correction
  ↓
learn
  ↓
reclassify
  ↓
sync
```

The difference is that dog names are no longer assumed to exist before the operator creates them.

## Product principles

* Identity records are authoritative in `state.db`.
* Dog names must be dynamic data, not hard-coded UI constants.
* A clean project should start with zero dogs.
* The operator must be able to manage dogs without editing the database directly.
* The review and learning pipeline must continue to work with user-managed identities.
* Existing learned examples and review history must remain valid.

## Functional requirements

* The system exposes a dog identity collection backed by persistent storage.
* The web UI can create a new dog identity.
* The web UI can rename a dog identity.
* The web UI can remove a dog identity when it is safe to do so.
* The review and learning paths read available dog identities from storage.
* No default dog names are injected into a clean database.
* Existing pipeline and sync behavior remains unchanged except for using dynamic dog identities.

## Non-goals

* Multi-user authorization.
* Collaborative dog ownership.
* Advanced identity metadata beyond what the current product needs.
* Replacing the review-learning pipeline.
* Introducing a new ML model.
* Automatically inferring a dog list from Immich.

## Acceptance criteria

* A fresh installation starts with no dog identities.
* Dog identities can be created, renamed, listed, and removed through supported application flows.
* The UI no longer relies on hard-coded Fibs/Hermann/Henri choices.
* Review and learning continue to operate against the dynamic identity store.
* Existing tests and checks pass with the dynamic model.
* Documentation reflects that dog identities are operator-managed data.

## Open questions

* Should identity deletion be blocked when learned examples or review history still reference the dog, or should the UI only support archive/disable behavior?
* Should the add/edit flow live directly inside Mission Control, or in a dedicated dog-management view?
* Should review-time identity suggestions be filtered from the current stored dog list only, or also include recently learned identities with no examples?
