# v1.2 Visual Style Refresh

## Purpose

The web UI grew feature-by-feature (Mission Control, Review, Job Queue, Metrics) with a
consistent component library (shadcn-style `Card`/`Button`, Tabler icons) but no unified visual
identity: a horizontal pill nav, ad-hoc decorative gradients on hero cards, and stat counts
presented as plain numbers rather than a scannable dashboard. This spec defines a single visual
design system -- navigation shell, color roles, stat-tile pattern, chart styling -- and applies it
across every existing tab so the app reads as one product rather than a collection of screens
built at different times, per [ux-principles.md](ux-principles.md) principle 20.

The reference target is an operator-supplied dashboard mockup: a fixed dark sidebar for
navigation, a light content area, color-coded stat tiles with icon badges, and card-based charts.

## User story

As the operator, when I move between Mission Control, Review, Job Queue, and Metrics, I want the
navigation, color language, card style, and action-button treatment to look and behave the same
way everywhere, and I want the Metrics tab to show real trend and breakdown charts instead of a
plain number grid, so the app feels coherent and I can read status at a glance.

## Goals

- One navigation shell (a fixed dark sidebar) replaces the current horizontal pill header,
  used on every page.
- One primary/action accent color (blue) replaces amber/orange as the app's action-button and
  active-nav-state color. This supersedes the color named in
  [ux-principles.md](ux-principles.md) principle 2 -- the *rule* (one shared, consistent action
  color, applied identically everywhere) is unchanged, only which color it names.
- A reusable "stat tile" pattern (icon in a colored circle, label, big number, short subtext,
  optional inline progress) replaces the current plain `CardHeader`/`CardTitle` number blocks used
  for dashboard counts.
- Status/category colors (good/warning/serious/critical, plus a small categorical set for
  non-status series) are used consistently for the same concepts everywhere they appear: job
  status badges, review-queue counts, and chart series all agree with each other.
- The Metrics tab gets real charts built from data `GET /metrics` already returns: a donut/ring
  breakdown of the eligible population (confident / review queue / unknown) and a pass-over-pass
  trend line, replacing the current stat-grid-only layout. Charting follows the project's
  `dataviz` guidance (validated categorical palette, one axis per chart, legend + direct labels,
  hover tooltips, accessible table fallback not required at this scale but color is never the only
  signal).
- Existing functional behavior (routes, API calls, keyboard shortcuts, review correction/skip
  flow) is unchanged. This is a presentation-layer refactor.

## Non-goals

- No new pages, routes, or navigation items beyond the four that exist today (Mission Control,
  Review, Job Queue, Metrics). The mockup shows a larger nav (Dogs, Albums, Settings) than this
  app currently has; adding those is a product-scope decision for a future spec, not a byproduct
  of a style refresh.
  **Amended** (see [DT-1107](../tickets/DT-1107-dogs-own-tab.md)): dog management was moved out of
  Mission Control into its own `/dogs` page and nav item, on explicit request, once the sidebar
  existed to hold it. Albums and Settings remain non-goals -- nothing has asked for those yet.
- No backend or API changes. Every chart and stat tile is built from fields `GET /metrics`,
  `GET /jobs`, `GET /review/stats`, and `GET /diagnostics` already return. In particular, no
  per-dog coverage breakdown and no "predictions changed" sub-category breakdown (improved /
  different dog / now unknown) -- `GET /metrics` only returns an aggregate `changed_count`, not
  that breakdown. Adding either is a candidate for a future ticket, not this one.
- No "average similarity/confidence score" chart. Carried forward from
  [v1.0.0.md](v1.0.0.md) section 8 and the v1.1 spec's non-goals: the nearest-neighbor similarity
  score is not a calibrated accuracy or probability, and charting it invites exactly that
  misreading without a held-out evaluation set.
- No dual-axis charts, even though the reference mockup's "Progress Over Time" chart uses one
  (images on the left axis, labeled-example count on the right axis). Per the `dataviz` skill,
  a dual y-axis is treated as the most common charting mistake, not a style choice to imitate.
  Where the mockup pairs two differently-scaled measures on one chart, this spec instead uses
  small multiples (two single-axis charts) or a shared unit.
  **Amended** (see [DT-1108](../tickets/DT-1108-progress-metric.md)): after this shipped as two
  single-axis charts, the user asked twice, with a reference design, for the combined dual-axis
  version -- and that design mitigates the usual ambiguity (axis title/ticks colored to match
  their series, a direct label on every point, a full-breakdown hover tooltip) rather than
  ignoring it. DT-1108 replaces the two charts with one dual-axis chart on that basis. The
  general principle (default to one axis; a second axis needs a specific, mitigated reason) still
  applies to future charts on this page.
- No change to the Review page's interaction model, keyboard shortcuts, or information density.
  Per ux-principles.md principle 21, correctness/clarity/speed for the human reviewer outrank
  visual consistency; the Review page gets the new shell chrome (sidebar, typography, button
  color) but its card/workflow internals are left alone.

## Requirements

### FR-1: Sidebar navigation shell

Replace `Header.tsx`'s horizontal pill nav with a fixed-width vertical sidebar, present on every
page via `AppShell`:

- App identity (logo/name) at the top.
- One nav entry per existing route (Mission Control, Review, Job Queue, Metrics), each with a
  Tabler icon and label. The active route is visually distinct (background highlight), following
  the existing pattern of not adding hover/mouseover animation to non-action nav elements
  (ux-principles.md principle 2's "non-action surfaces" rule extends to nav items).
  Review's nav entry keeps the pending-review-count badge that exists today (previously shown as
  a numeral in the page itself).
  Restoring/expanding this only requires code that already reads `ReviewQueueStats.remaining` from an
  existing call, not a new endpoint.
- The theme toggle moves into the sidebar (bottom section), replacing its current position in the
  horizontal header.
- The sidebar keeps a fixed dark appearance regardless of the light/dark content theme -- it is
  chrome, not content, matching the reference mockup and common dashboard convention (e.g. the
  content area still fully respects the light/dark toggle).
- On narrow viewports the sidebar collapses to icon-only or a top bar, consistent with
  ux-principles.md principle 15 (responsive by default) -- this app's primary environment is
  desktop, but the sidebar must not make the app unusable at typical laptop widths.

### FR-2: Primary accent color

Replace the amber/orange `--primary` (and dependent `--ring`, active-nav-highlight) tokens with a
blue accent, in both light and dark theme. `Button`'s `default`/`secondary`/`outline`/`ghost`
variants, which already derive from `--primary`, need no per-component changes -- only the token
definition changes. `ux-principles.md` principle 2 is updated to name blue instead of orange as
the shared action-button color; the principle itself (one consistent, shared action color,
applied identically everywhere) is unchanged.

### FR-3: Status and categorical color roles, used consistently

Adopt a small, validated palette (see Design notes) with two kinds of roles:

- **Status roles** (good / warning / serious / critical) for anything that represents a state:
  job status (running/completed/failed/pending/canceled), review-queue urgency, confident vs.
  needs-review vs. unknown classification counts. The same status maps to the same color
  everywhere it appears (e.g. "confident"/"completed"/"good" is always the same green, whether
  it's a stat-tile icon, a donut segment, or a job badge).
- **Categorical roles** for data series that are not a status (e.g. the labeled-example-count
  trend line, which is neither good nor bad, just a count that grows over time).

Status/categorical colors reinforce meaning alongside an icon and/or text label -- never as the
only signal, per ux-principles.md principle 13.

### FR-4: Stat-tile pattern

Introduce one reusable stat-tile component (icon in a colored circle, label, large value, short
subtext, optional inline progress bar) and use it everywhere a page currently shows a bare
`CardHeader`/`CardTitle` number: Mission Control's job/review counts, Metrics' coverage/review
rate/queue/labeled-example/last-reclassify tiles.

### FR-5: Metrics charts

Add to the Metrics page, using only existing `GET /metrics` fields:

- A donut/ring chart of the eligible population split into confident / review queue / unknown,
  using the status color roles from FR-3, with a legend and direct value labels (not color alone).
- A pass-over-pass trend chart (from `pass_history`) of review-queue size, confident count, and
  unknown count on one shared axis (all three are "count of eligible crops", so they share a
  unit and belong on one chart, per FR-3's color roles).
- A separate single-series trend of labeled-example count over the same passes, kept as its own
  chart rather than a second axis on the chart above (see Non-goals).
- All existing stat tiles (coverage, review rate, review queue, labeled examples, last
  reclassify) restyled per FR-4, with the automation-rate headline number kept as the page's most
  prominent element.

### FR-6: Manual-operations quick actions

Mission Control's two most common operations (Run pipeline, Reclassify) get prominent buttons in
the page header (solid primary + outline secondary, matching the reference mockup's pattern),
while the existing "Manual Operations" card -- which also covers Sync and carries the
descriptive text each operation needs (ux-principles.md principle 3: unfamiliar operations need
text, not just an icon) -- stays as-is further down the page. The header buttons are a shortcut
to the same job-creation call the card's buttons already use, not a new code path.

## Acceptance criteria

- Every page (Mission Control, Review, Job Queue, Metrics) renders inside the same sidebar shell,
  in both light and dark theme.
- No component hardcodes an amber/orange hex or `rgba(251,191,36,...)`-style value for an action
  or brand accent; all such values come from the `--primary` design token or the FR-3 status/
  categorical roles.
- Job status badges (Job Queue, Mission Control's recent-jobs list), the Metrics donut, and the
  Metrics trend chart use the same color for the same status (e.g. "failed" and "critical" are
  always the same red).
- The Metrics page's donut and trend charts render from live `GET /metrics` data, degrade
  gracefully (no chart, not a broken one) when `pass_history` has fewer than 2 entries, and never
  present the nearest-neighbor similarity score as accuracy/probability.
- `npm run build` and `npm run lint` pass with no new warnings introduced by this change.
- The Review page's correction/skip/keyboard workflow is unchanged -- verified by exercising it
  in a browser, not just by inspecting the diff.
- Backend code, database schema, and API responses are untouched by this spec.

## Design notes (non-normative detail supporting the requirements above)

- **Palette source**: the project's `dataviz` skill ships a pre-validated, colorblind-safe
  categorical/status palette (`references/palette.md` in that skill). This spec reuses it rather
  than hand-picking new colors: categorical slot 1 (blue, `#2a78d6` light / `#3987e5` dark)
  becomes `--primary`, so the brand accent and the first chart series are the same blue by
  construction. The status roles (good `#0ca30c`, warning `#fab219`, serious `#ec835a`, critical
  `#d03b3b`, same hex in both themes) drive job-status badges, the Metrics donut, and the Metrics
  trend chart identically.
- **Sidebar tokens**: implemented by fixing the existing (currently unused) `--sidebar*` CSS
  custom properties to the same dark values in both `:root` and `.dark`, rather than introducing
  a parallel set of tokens.
- **Neutral palette**: the app's pre-existing base tokens (`--background`, `--foreground`,
  `--card`, `--popover`, `--secondary`, `--muted`, `--accent`, `--border`, `--input`, in both
  themes) carried a warm cream/amber tint (OKLCH hues ~30-80) left over from the pre-refresh
  theme -- it didn't match the reference mockup's clean white/cool-gray surfaces and clashed with
  the new blue accent and navy sidebar. These were re-stepped to a low-chroma cool gray sharing
  the sidebar/primary hue family (~258-260) rather than a warm one, so the whole app (not just the
  sidebar and accent) reads as one cohesive cool palette. Status/categorical colors are unchanged
  -- warmth there (e.g. the amber warning, red critical) is semantically correct, not a leftover.
- Chart implementation stays hand-rolled SVG (the existing `CoverageSparkline` pattern), not a
  new charting dependency -- consistent with keeping the dependency footprint small and matching
  how the one existing chart in this codebase was already built.

## Open questions (resolved)

- **Should the primary accent become blue (matching the mockup) or stay amber with the mockup's
  layout only?** Resolved with the requester: adopt blue everywhere, superseding the amber
  guidance in `ux-principles.md`.
- **Does this spec add the mockup's Dogs/Albums/Settings nav items?** Resolved: no -- out of
  scope, see Non-goals. This is a visual-style refresh of the app's existing four tabs, not an
  information-architecture change. (Dogs was carved out later as a deliberate, separately
  requested amendment -- see the Non-goals note and DT-1107. Albums/Settings are still out of
  scope.)
