# v1.7.0 — Pluginable Insight Providers

Tracking issue: [#110](https://github.com/bradreimer/immich-dog-tagger/issues/110).

## Purpose

v1.6.0 ([#94](https://github.com/bradreimer/immich-dog-tagger/issues/94),
[docs/specs/v1.6-pet-insights.md](v1.6-pet-insights.md),
[ADR-004](../adr/ADR-004-pet-occurrence-observations.md)) shipped a "fun layer" of derived facts
about each confirmed pet identity — total photos, favourite place, favourite human (surfaced as a
qualified count, e.g. "Most often with Brad (112 photos)"), and Immich-favorite count — computed
at read time from the `PetOccurrence` fact table so nothing is ever stored as a stale conclusion.
That spec's Non-goals deliberately deferred a second wave of facts of the same shape: Milestones
(e.g. "this was Hermann's 1000th confirmed photo"), On This Day, Best Friends (pet-to-pet
co-occurrence), and a Pet World Tour map.

Today, every fact `InsightsService` produces is a bespoke method (`summary`, `timeline`, `places`,
`people`) that owns its own aggregation logic inline. Landing each deferred item the same way means
growing that one file and its typed API surface by one method and one endpoint per fact,
indefinitely. This spec makes the *mechanism that determines a fun insight* — not just the facts
themselves — a pluggable unit: a self-contained provider that can be added, tested, and reviewed
independently of `InsightsService`'s core code, its API routes, and every other provider.

## User story

As a maintainer adding a new fun fact (a Milestone, On This Day, Best Friends, or anything similar
later), I want to implement and register one self-contained provider, so that landing it never
requires editing `InsightsService`'s existing methods, adding a new typed endpoint, or touching
unrelated facts — the same way a new classifier scoring rule doesn't require rewriting the
classifier that runs it.

As an owner viewing a dog or cat's Insights page, I want new fun facts to appear automatically as
they're added, without waiting on frontend work for each one individually.

## Goals

- Define a single `InsightProvider` interface: one provider computes one fact from existing
  `PetOccurrence` + `Asset` data (the same inputs `InsightsService` already reads — no new source
  of truth, no change to what data insights are allowed to depend on).
- Provide an explicit, in-process registry of providers — adding a fact means adding one file and
  one line in the registry list, not touching a growing conditional or a shared aggregation method.
  No dynamic/third-party plugin loading (see Non-goals) — "pluginable" here means the codebase's own
  insight logic is organized as independent, addable units.
- Migrate the existing opinionated single-fact insights — favourite place, favourite human,
  Immich-favorite count — onto this same mechanism, so there is exactly one system that determines
  every fun insight, present and future, not a legacy path plus a new one.
- Add a generic, read-only surface (`GET /api/dogs/{id}/insights/cards`) that renders whatever
  providers are currently registered, so a new provider shows up in the UI with no frontend change
  per insight.
- Land at least one new insight from v1.6.0's deferred list under this architecture as
  end-to-end proof, not just the framework: a Milestones provider (e.g. "1000th confirmed photo").
- Keep every provider computed at read time, per [ADR-004](../adr/ADR-004-pet-occurrence-observations.md)
  — no provider writes a conclusion back to `state.db`, and a provider with insufficient data
  returns nothing rather than a fabricated placeholder.

## Non-goals (this iteration)

- Dynamic or third-party plugin loading (`entry_points`, loading arbitrary installed packages,
  a plugin marketplace). This is a local-first, single-operator tool — extensibility means "easy to
  add to this codebase," not "installable from outside it." Revisit only if a real need for
  out-of-tree providers appears.
- Per-provider enable/disable settings or an owner-facing configuration UI for which insights show.
  All registered providers run for every request; hiding one means removing it from the registry.
- On This Day, Best Friends, and Pet World Tour map. The architecture is built to make each of
  these a follow-up provider with no further core changes, but only the Milestones provider ships
  in this iteration, as the mechanism's proof.
- Removing or reshaping the existing `timeline`/`places`/`people` list endpoints. Those return
  ranked collections, not a single fact, and don't fit the one-provider-one-card shape — they stay
  exactly as they are.
- A materialized/precomputed insights cache — still out of scope per ADR-004's existing reasoning;
  this spec changes how facts are organized in code, not the "compute fresh every request" policy.
- Any personality inference, AI-generated narrative text, or writing conclusions back to Immich —
  unchanged from v1.6.0.
- Endpoint-level API auth — unchanged existing gap (`docs/status.md`).

## Requirements

### `InsightProvider` interface

A `Protocol` (matching the existing `Embedder`/`Clock` pattern in this codebase — a plain
structural interface, no base class or decorator magic):

```python
class InsightScope(str, Enum):
    IDENTITY = "identity"  # only needs this identity's own occurrences
    LIBRARY = "library"    # needs a cross-identity query (e.g. Best Friends)

@dataclass(frozen=True)
class InsightCard:
    slug: str
    title: str
    value: str
    subtext: str | None
    category: Literal["volume", "place", "social", "milestone", "time"]

@dataclass(frozen=True)
class InsightContext:
    identity: Identity
    occurrences: list[PetOccurrence]  # this identity's own, joined to Asset
    session: Session  # escape hatch for LIBRARY-scope providers only
    now: datetime      # injected, not datetime.now(), so On This Day is testable

class InsightProvider(Protocol):
    slug: str
    title: str
    category: str
    scope: InsightScope

    def compute(self, context: InsightContext) -> InsightCard | None: ...
```

Returning `None` means "not enough data for this identity yet" (e.g. Milestones before the
identity's photo count reaches a threshold) — never a fabricated zero or placeholder, matching
ADR-004's existing rule for `top_place`/`top_person`.

### Registry

`src/immich_dog_tagger/services/insights/providers/__init__.py` exports one explicit list:

```python
INSIGHT_PROVIDERS: list[InsightProvider] = [
    TotalPhotosMilestoneProvider(),
    FavouritePlaceProvider(),
    FavouriteHumanProvider(),
    ImmichFavoritesProvider(),
]
```

Explicit and hand-maintained, not auto-discovered — consistent with CONTRIBUTING's "prefer simple,
explicit code" and this project's existing preference for small, direct abstractions over
frameworks (there is no registry/factory pattern anywhere else in the codebase; this introduces the
first one, deliberately kept minimal).

### Migrating existing insights

`favourite place`, `favourite human`, and `favorite_photo_count` — currently inline logic inside
`InsightsService.summary()` — become providers (`FavouritePlaceProvider`,
`FavouriteHumanProvider`, `ImmichFavoritesProvider`). `InsightsService.summary()` keeps its exact
current method signature and `InsightsSummary` return shape (no API/UI break); internally it builds
an `InsightContext` and pulls these three fields from the matching providers' `InsightCard.value`
instead of owning bespoke aggregation for them.

`total_photos`, `first_seen`/`last_seen`, and `photos_by_year` stay direct computation in
`InsightsService` — they're structural summary counts other providers depend on as building blocks
(e.g. Milestones needs the identity's ordered occurrence count), not opinionated "fun facts"
themselves. `timeline`, `places`, and `people` (full ranked lists, not single facts) are unchanged.

This phase is a pure refactor: existing tests (`tests/test_insights.py`, `tests/api/test_insights.py`)
must pass unmodified, proving no behavior change.

### New surface: insight cards

`GET /api/dogs/{identity_id}/insights/cards` (new, read-only, 404 if identity doesn't exist):
runs every registered provider against the identity (giving `LIBRARY`-scope providers session
access for cross-identity queries) and returns the list of non-`None` results as
`list[InsightCardResponse]`. A provider a pet doesn't yet have enough data for is simply absent
from the list — never a placeholder card.

UI: `DogInsightsPage.tsx` gains a new card grid section rendering whatever `/insights/cards`
returns, keyed by `category` for icon selection (one icon per category, not per specific insight,
so a new provider needs no frontend icon mapping to appear). The existing stat tiles
(`top_place`/`top_person`/etc., still served by `/insights/summary`) are unchanged — this is
additive, not a replacement of the existing page layout.

### First new provider: Milestones

`TotalPhotosMilestoneProvider` (`scope=IDENTITY`, `category="milestone"`): given an identity's
occurrences ordered by `asset.captured_at` (same ordering `timeline()` already uses), if the
identity has reached a round-number confirmed-photo count (100, 500, 1000, 5000, ...), returns a
card naming the milestone and which photo hit it (e.g. "1000th confirmed photo — March 2024"). No
schema change: this is computed entirely from the existing `PetOccurrence`/`Asset` data already
used by `timeline()`.

## Acceptance criteria

- Given the current `InsightsService.summary()` test suite, all existing assertions pass unchanged
  after `favourite place`/`favourite human`/`favorite_photo_count` are refactored into providers —
  proving the migration is behavior-preserving.
- Given a new provider file implementing `InsightProvider` and one line added to
  `INSIGHT_PROVIDERS`, `GET /api/dogs/{id}/insights/cards` includes its result with no other code
  change, and the UI renders it with no frontend change beyond the one-time card-grid section.
- Given an identity with fewer than 100 confirmed photos, `TotalPhotosMilestoneProvider` returns
  `None` and no milestone card appears — no fabricated "0/100" progress placeholder.
- Given an identity that crosses a milestone threshold (e.g. its 1000th `PetOccurrence` is
  created), the next call to `/insights/cards` reflects it immediately — computed at read time,
  nothing pre-materialized, matching ADR-004.
- `GET /api/dogs/{id}/insights/cards` 404s for a nonexistent identity, matching the existing
  `summary`/`timeline`/`places`/`people` endpoints' behavior.

## Open questions

- Should `LIBRARY`-scope providers (needed by a future Best Friends provider) get a shared,
  precomputed cross-identity occurrence index instead of each running its own query, once more than
  one such provider exists? Deferred until Best Friends is actually implemented — one `LIBRARY`
  provider's own bounded query is cheap enough to not warrant shared infrastructure yet.
- Milestone thresholds (100/500/1000/5000, or a configurable list) are a product-polish detail left
  to implementation; this spec only requires that the mechanism is threshold-based and read-time.
- Whether `favourite place`/`favourite human` should *also* appear as cards on the new
  `/insights/cards` surface (for a single unified feed) or stay exclusively in the existing
  `/insights/summary` stat tiles is left to implementation/UI polish — both are served by the same
  underlying providers either way, so this is a presentation choice, not an architecture one.
