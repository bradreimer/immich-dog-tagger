# v0.9.3 Production Validation & Pipeline Confidence

## Goal

Prove that the complete Dog Tagger operational loop works reliably against a real Immich library using the production architecture established by v0.9.0 through v0.9.2.

v0.9.0 established Mission Control and persistent jobs.
v0.9.1 established unattended scheduling.
v0.9.2 established backup, recovery, and operational safety.

v0.9.3 is the confidence release:

> Run the real system end-to-end, verify that every stage is observable and recoverable, and fix only issues discovered by that validation.

This release is deliberately not a feature-development milestone.

## Scope

Validate the complete operational loop:

```text
Immich
  ↓
scan
  ↓
detect
  ↓
crop
  ↓
embed
  ↓
classify
  ↓
Mission Control review
  ↓
correction
  ↓
learn
  ↓
reclassify
  ↓
sync
```

The same operations must work both manually from Mission Control and through the scheduler where applicable.

## **Production validation principles**

* Use the real Immich deployment on `schnorbit`.  
* Begin with a bounded validation dataset before processing the full library.  
* Never make destructive Immich changes as part of validation.  
* Preserve `state.db` through the v0.9.2 backup/recovery process.  
* Prefer incremental/idempotent processing.  
* Record enough information to explain what happened.  
* Fix production defects discovered by validation, but do not add speculative features.

## **Dataset validation**

Validation should proceed in stages:

1. Small representative sample.  
2. Larger representative sample.  
3. Full-library incremental run.

The representative sample should include:

* known dogs  
* multiple dogs in one image  
* unknown dogs  
* low-confidence classifications  
* candidate conflicts  
* images spanning relevant years  
* images with imperfect/missing metadata  
* already-processed assets  
* assets requiring incremental processing

## **Pipeline invariants**

Validation must establish that:

* repeated scans do not duplicate assets  
* repeated detection does not duplicate detections  
* repeated crop/embedding work is safely incremental  
* classification is repeatable for unchanged inputs  
* review corrections persist  
* review corrections create learning examples  
* learning improves subsequent classification where expected  
* historical capture metadata remains available to learning  
* sync does not create unintended duplicate organization  
* scheduled and manual execution share the same job infrastructure

## **Review validation**

Use real review items to validate:

* unknown classification  
* low-confidence classification  
* candidate conflict  
* correct identity  
* incorrect identity correction  
* skip  
* repeated review of the same item  
* learning from corrections

The test must verify both UI behavior and authoritative `state.db` state.

## **Learning validation**

Measure learning qualitatively and quantitatively where practical.

At minimum:

* establish a baseline classification result  
* add a controlled set of human corrections  
* run learning  
* reclassify affected examples  
* verify that expected examples improve  
* verify that unrelated identities are not unexpectedly corrupted

Do not promise a numerical accuracy threshold unless the existing project has a defensible evaluation dataset.

## **Sync validation**

Validate Immich synchronization in a safe mode first.

Confirm:

* intended albums are created/updated  
* expected assets are represented  
* repeated sync is idempotent  
* no unintended assets are removed  
* failures are visible in job history  
* state.db remains authoritative

## **Performance and operational validation**

Capture useful production observations:

* elapsed time by major operation  
* job counts  
* failures/retries  
* database growth  
* derived-data growth  
* GPU/CPU/memory behavior where readily available  
* scheduler behavior during long-running jobs

Do not turn this into a benchmarking project. Capture enough information to identify obvious production problems.

## **Defect handling**

If validation finds defects:

* create a focused follow-up ticket  
* fix the smallest root cause  
* add a regression test  
* rerun the affected validation stage  
* avoid changing the roadmap unless the defect exposes a fundamental architectural problem

## **Exit criteria**

v0.9.3 is complete when:

* representative production data has completed the full pipeline  
* the full library has been processed incrementally or a documented production-scale run has completed  
* Mission Control has been used for real review work  
* review corrections have been learned from successfully  
* reclassification reflects learned examples  
* sync has been validated safely  
* scheduled execution has been exercised against real work  
* restart/recovery behavior has been exercised during operational work  
* no known data-loss or duplicate-work defect remains  
* observed production issues are fixed or explicitly documented for v1.0  
* `./scripts/check.sh` passes
