# v1.5 Automatic Temporal Classification

## Purpose

DT-1114 (v1.4.0) added an optional owner-set active date range per identity
(`Identity.active_from`/`active_until`) so the classifier could flag a candidate match whose
photo was taken outside that identity's known window. In practice this asks the owner to keep
per-dog/cat date ranges up to date by hand -- including remembering to set an end date when a pet
passes away, and a start date for a new, possibly visually similar, pet. The owner has asked for
this to happen automatically instead: use the photo's own capture date, weigh how well a
candidate's known reference examples align with it, and let that carry the signal that a manual
range used to -- covering appearance change over a pet's life, a pet passing away, and a new
similar-looking pet arriving, with no configuration step.

This spec reverses v1.4's Non-goals decision that active ranges must be "explicit owner input --
never inferred," and supersedes FR-4/FR-5 of
[v1.4-trustworthy-photo-library.md](v1.4-trustworthy-photo-library.md) accordingly. The owner has
confirmed this may change `state.db`'s schema and that they will start from a fresh database.

## User story

As the owner, I don't want to maintain a start/end date per dog or cat by hand. I want
classification to automatically favor whichever identity's known photos are closest in time to
the photo I'm classifying, so an aging dog's changing look, a dog that has passed away, and a new
dog that happens to look similar are all handled without me configuring anything.

## Goals

- Remove the manual active-date-range fields, API, and UI entirely (DT-1114's `active_from`/
  `active_until` mechanism).
- Score each candidate example using both visual similarity and how closely its own capture date
  aligns with the photo being classified, relative to *that photo's* date -- not wall-clock "now"
  -- so classifying an old photo still correctly favors examples from that same era.
- Weight examples captured within about a year fairly strongly, decaying gradually beyond that,
  with a floor that never reaches zero -- a lone identity with only old examples and no
  closer-in-time competing identity must still classify correctly.
- Fail open exactly as DT-1114 did: a photo or an example with no capture date participates at
  full weight. Absence of date evidence is never a penalty.
- Never let the temporal signal manufacture, inflate, or deflate the reported confidence number
  for the winning match -- it only influences *which* example/identity wins the comparison,
  preserving the existing rule that `similarity` stays a raw, uncalibrated embedding score (see
  [v1.0.0.md](v1.0.0.md) section 8, and DT-1114's own `date_conflict`, which followed the same
  principle).
- Replace the hard-boundary `date-conflict` review reason with a continuous-weighting-aware
  signal, so the owner still sees "why is this uncertain" without configuring anything.

## Non-goals

- No automatic date-of-birth/date-of-death inference or computer-vision age estimation (unchanged
  from v1.4's Non-goals -- this spec changes *how existing capture-date evidence* is used, not
  what counts as evidence).
- No owner-facing setting to tune the decay curve (its characteristic ~1 year scale, or its
  floor) in this pass. Ship one sane default as a code constant; revisit if usage shows it's
  wrong for a real library, per Open Questions.
- No change to the underlying nearest-neighbor approach beyond this scoring adjustment: still
  per-example cosine similarity, still one winning example per identity, still governed by
  `ClassifierPolicy`'s threshold and candidate limit.
- Does not retroactively recompute existing `CropClassification` rows. The next Reclassify pass
  (the existing mechanism for any classifier-version change) picks up the new scoring.

## Requirements

### FR-1: Remove the manual active-range mechanism

Delete `Identity.active_from`/`active_until` and their migration
(`_ensure_identity_active_range_columns`), `DogService.set_active_range`,
`PUT /dogs/{id}/active-range`, `DogActiveRangeRequest`, and the "Active from"/"Active until" date
inputs on the Dogs & Cats page (`DogManagementCard.tsx`).

### FR-2: Temporal weight as a function of capture-date proximity

`SimilarityScorer` computes a `temporal_weight` in `[floor, 1.0]` from the absolute difference
between the crop's `captured_at` and a candidate example's own `captured_at`: `1.0` when the
dates coincide, decaying toward a floor (never reaching it) as the gap grows, with a
characteristic scale of about a year. `temporal_weight` is `1.0` whenever either date is missing
-- the same fail-open guarantee DT-1114 made for `date_conflict`.

### FR-3: Weighted ranking, unweighted reported confidence

For each identity, `IdentityClassifier` selects the example that maximizes
`similarity * temporal_weight` (not raw similarity alone) as that identity's best match, and
ranks candidates by the same combined score. The `similarity`/confidence reported for the winning
candidate remains that example's raw cosine similarity -- `temporal_weight` decides *which*
example/identity wins, never what confidence number is shown or compared against
`ClassifierPolicy.confident_threshold`.

### FR-4: Candidate transparency

`ClassificationCandidate` exposes `temporal_weight` (replacing `date_conflict`), persisted in
`CropClassification.candidates` exactly as `date_conflict` was.

### FR-5: Review reason

`ReviewQueryService._review_reason()` surfaces `temporal-mismatch` (replacing `date-conflict`)
when the accepted/top candidate's `temporal_weight` falls below a fixed low-alignment threshold.
A candidate whose weight is `1.0` -- whether because the dates aligned or because a date was
missing -- is never flagged, preserving fail-open behavior.

### FR-6: Schema

Drop `active_from`/`active_until` from `Identity` and remove their additive migration. No
backward-compatible migration path is provided for existing databases; the owner has confirmed
they will start from a fresh `state.db`.

## Acceptance criteria

- The Dogs & Cats page no longer shows or lets the owner edit an active-date range.
- Classifying a photo whose capture date sits close to one identity's own example dates, and far
  from a visually similar competing identity's example dates, selects the temporally closer
  identity even when raw cosine similarity between the two candidates is nearly equal (covers:
  disambiguating a deceased pet's identity from a new, similar-looking pet's, automatically,
  using only each identity's own photo history).
- Classifying a photo with an unknown capture date, or against an identity whose examples all
  lack capture dates, behaves exactly as it would with temporal weighting disabled (uniform
  weight of `1.0`).
- A single-identity candidate with no competing identity still reports its true raw similarity as
  confidence regardless of how old its examples are -- old examples alone, with nothing to
  disambiguate against, must not demote an otherwise-confident match to needs-review.
- Tests covering the removed `date_conflict`/active-range behavior are replaced with equivalent
  temporal-weighting coverage: recency breaks a near-tie, the floor prevents a distant example
  from being fully excluded, missing dates fail open, and a deceased-pet/new-lookalike scenario
  resolves to the temporally correct identity.

## Open questions

- Should the decay curve's scale/floor become an owner-tunable setting (e.g. "how quickly should
  older photos of a pet stop mattering") rather than a fixed constant? Starting fixed; revisit if
  real usage shows the default doesn't fit a particular library (e.g. very long-lived, slow-to-
  change breeds vs. fast-growing puppies).
- Should Reclassify's pass summary report how many classifications changed identity specifically
  because of temporal weighting (vs. any other cause)? Not scoped here -- the existing
  `changed_count` already captures "did the identity change" without attributing why.
